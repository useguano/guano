## What this is

A browser-based visual website builder. The user builds pages on a live canvas with a **Layers tree** — inserting and arranging elements, then styling them. A page's structure is an `ElementNode` **tree**, and the tree is all there is: no text format sits beside it (there was an indentation DSL until the v2 schema; see the migration below). AI agents read and write the same tree as a strict **HTML** subset. The canvas lets them style elements, add interactions, leave comments, branch/merge, translate into locales, and build reusable components and CMS collections. There is **one admin shell** (`BuildView` at `/admin`, laid out by `EditorLayout`) with **two surfaces** over one shared document, switched by the **Edit / Play** toggle at the bottom-right of the page canvas (`ModeToggle`; the bottom-left corner is the ⌘E Insert dock's) — a runtime mode in `useViewMode`, **not a route**. **Edit / Play is the UI's whole vocabulary for this; the internals stay `build`/`preview`** (`mode`, `isBuild`, `isPreview`, `SitePreview`, `PreviewRenderer`), and `ModeToggle` is the one place both names appear:

- **Build** (shown as **Edit**) — the left **rail** (`AppRail`), one optional 16rem **column** (Pages or Components — a page's and a component's **layers** are edited inside them), the infinite **canvas** — the open page's breakpoint frames (`CanvasEditor` → `ElementRenderer`) or the components board (`ComponentsBoard`) — and the right **settings rail + panel** (`SettingsEditor`).
- **Preview** (shown as **Play**) — the Build-only columns drop out and the centre becomes the full-site render (`SitePreview` → `PreviewRenderer`). For an admin or editor it is **read-only**: the site the way a visitor gets it, with links navigating (state-driven, no URL change), interactions, animations, scrub, sliders and smooth scroll all running for real, no editor affordance drawn over it, and text edited on the Edit canvas (`ElementRenderer`). Anyone can add a **comment** (hold C, click). **A contributor also edits content on the render** (`usePreviewEditing`, gated on `!canBuild`): double-click text to edit it in place (`useInlineEdit` with `escBehavior: 'save'`; field-bound text writes the entry, locale-aware), double-click an image/video to replace it from the media library, and right-click for **Edit content** / **Replace background** (the menu lives in `SitePreview`). Text inside a component instance is per-instance content, so it is editable; a background inside one is the master's (`backgroundInfo` renders from it, and the contributor merge keeps masters), so it is not offered. While editing is on, a link's single click waits 250ms (one shared `pendingNav` timer) so a double-click can cancel it; for builders a click navigates at once. The chrome around it still edits: the sidebar panels are per account type, not per mode, so an admin keeps the full Data/Style/Interactions inspector in Play, and the Pages drawer keeps its page/item settings. **Contributors are pinned here** (`useViewMode` forces the mode the moment `canBuild` resolves false; the Components rail button, the Pages drawer's Edit-layers icons and the toggle itself are hidden for them, so they only ever see Play and never learn there was a switch) — which means a contributor's content editing is the in-place editing above, plus the **Pages drawer's** item/page settings (entry field values, name/slug/status/seo) and comments.

The toggle is a **page's** mode, so `BuildView` mounts it only when `canBuild && !showComponents` — the components board has nothing to play, and you leave it by opening a page. Leaving Edit closes the ⌘E palette (`ModeToggle` calls `closePalette`, not `setMode`, so the view-mode singleton never pulls in `useStructure`). It sits bottom-RIGHT so it never shares a corner with `InsertDock`, and its Play offset pays back the framed pane's `my-2` + border so switching doesn't move it under the pointer.

Tailwind v4 (via `@tailwindcss/vite`), CSS-first with no config file — theme tokens live in `src/assets/main.css`. `@tailwindcss/browser` is dynamically imported in `CanvasEditor` so classes typed at runtime (and the project's design tokens) compile on the fly.

## Routes (`src/router/index.ts`)

The SPA is the **admin editor only**, served under `/admin/` (Vite `base: '/admin/'`, so route paths are base-relative). The published site is the static export served by the node server at `/` — it never enters the Vue app. Routes: `/` (`build` — the whole editor, both surfaces), `/login`, `/setup` (first-run), `/invite/:token` (`SetPasswordView`, accept invite), plus a catch-all redirect to `/`. Preview stopped being a route when the two views merged into one shell, and no legacy path is kept as a redirect — the app is not public, so there are no old bookmarks to honour. A `beforeEach` guard gates everything on auth (redirecting to `/setup` or `/login`); there is no role redirect — contributors reach the same route and are pinned to the Preview surface by `useViewMode`. Hard `window.location.assign('/admin…')` calls (login/logout flows) use full server URLs and keep their `/admin` prefix.

## State model: composable singletons

Shared state is module-level `ref`s declared **outside** the exported composable function, so every caller of e.g. `useProject()` sees the same instance — a hand-rolled store. This is the backbone; follow it for new global state. Two flavors: composables that derive from the `project` document, and newer server-hydrated ones (`useAuth`, `useUsers`, `useBranches`) that hold data fetched from the API.

- `useProject` — owns the single `project` ref (the whole document) and project-level ops.
- `usePage` — active page selection, page CRUD, keeps each page's `@setup` in sync with its `code`.
- `useElement` — selection/drag/highlight state + **all structural mutations** (add/remove/duplicate/paste/reorder/change-type/set-arg). Selection defaults to the page body when nothing is picked.
- `useEditorBoot` — admin-zone boot: `await hydrateStore()` then start autosave/sync. Module-scoped `started` flag so it runs exactly once however the shell mounts. Autosave and undo therefore run in the Preview surface too, not just Build.
- `usePersistence` — autosave + undo/redo + which branch is loaded (`docs/server.md`).
- `useInteraction` (class toggles), `useAnimation` + `useMotion` (tween timelines), `useComments`, `useComponents`, `useCollections`, `useBranches`, `useLocale`, `useContextMenu`, `usePanel`, `useSettings`, `useThemeTokens` — one subsystem each.

`Project` (`src/types/editor.ts`) is the whole serializable document: `pages`, `components`, `collections`, `interactions` + `animations` (the two shared motion libraries), `breakpoints`, `comments`, `locales` + `defaultLocale`, and `settings` (`ProjectSettings`: design `tokens`, seo, favicon, domain, smtp, custom code, fonts). Runtime-only state (selection, camera, open popover, fired interactions, **active locale**, active branch id) lives in composables and is intentionally **not** part of the project or its history.

## The core invariant: the tree is the source of truth for structure

A `Page` has `elements` — the `ElementNode` tree — and **that is the whole of its structure**. There is no second representation to keep in step. Every structural change — insert, drag-reorder, duplicate, delete, wrap, retype — mutates the tree directly, through `lib/treeOps`.

Tree edits carry identity for free, which is the point: the node objects survive, so ids, per-node state, selection and interaction `targetId` cross-references do too. Identity has to be *matched* in exactly two places now — realigning an instance to its master (`alignStructure`), and applying an agent's HTML (`lib/html/apply.ts`) — and both are documented below.

`alignStructure` keeps the node object for every child its signature-LCS pairs and leaves an already-current subtree byte-identical — a push that reads as an edit would be adopted straight back over the edit.

`node.classes`, `node.content`, `node.locales`, `node.arg`, `node.ref`, `node.link` — all of it is just node state now, mutated in place. (`arg`, `ref` and `link` used to be "code-owned" and patched into the text; the only thing left of that is that inside a component instance **`arg`** belongs to the master, so the push copies it down. **`link` does not**: it is per-instance with a component default, because one Button component serves a dozen destinations — every renderer resolves it along the CHAIN (`resolveInstanceValue`: own, then each host's mirror, then the master), and `adoptCodeOwned` deletes an instance link only when it equals what that node would INHERIT, so the key means "this placement differs" and nothing else. **Inherit, not `master.link`** (`effectiveLinkChain`, computed once per push): a master-side counterpart is very often a mirror, and a mirror carries `link` only when the host overrode it, so comparing against the counterpart's own key never recognized a page copy of a NESTED component's default as redundant. That copy survived every push, sat first in the chain, and permanently shadowed whatever the host later set on its mirror — a Nav aiming its Button mirror at `#signup` kept publishing Button's own `/contact`, with `applied: link` on the write. Normalization happens in `pushMasterStructure`, which every component op routes through, so a project carrying an old shadow is repaired by the next push on that host. Coverage: `e2e/mcp-component-links.spec.ts`.)

## The v2 schema and its migration (`src/lib/migrate.ts`)

v1 stored an indentation DSL beside the tree — `page.code`, plus a `line`/`endLine` on every node — because the text was authoritative for structure. v2 deletes all of it, and with it the four pure **alias** element types the DSL's registry carried (`container`, `grid`, `heading`, `dropdown` — each one only another name for a tag that already existed). `project.schemaVersion` records which shape a blob is in; absent means v1.

`migrateProject` is the one implementation, and it is **idempotent**, which is what makes "run it over everything, every boot" safe. It ensures each page has a body, materializes instances still stored as an unexpanded `:Card:` leaf, collapses the aliases, deletes `code`/`line`/`endLine`, and sets `schemaVersion`.

Three rules are load-bearing.

1. **The tree wins over the text, and nothing is re-derived from it.** This was not the original plan; the corpus disproved it. Over real projects `reconcile(code, code, elements)` *changes* the tree — a node carries a `link` its line never had, blocks are missing a closer so the parser nested their siblings — and in every case the tree is what every renderer read, so it is what the user was looking at and what the published site shows. Re-deriving would silently change live pages. The migration records the pages whose stored text disagreed (`report.textDisagreed`) and moves on.
2. **Collapsing an alias must render identically** (`check:migrate` and `check:corpus` both prove it), and the aliases stay in `ELEMENTS_DATA` as a render fallback: a blob the migration never saw must not degrade a `heading` to a bare div.
3. **Materializing an unexpanded instance is a FIX, not a no-op.** A stored `:Card:` leaf had no nodes, so it rendered as nothing at all — the page was silently missing its card. This is the one migration step that deliberately changes a render, and `check:migrate` asserts the change rather than the absence of one.

A page with text but no usable tree is **salvaged** through `src/lib/legacy/dsl.ts`, a salvage-only parser (no reconcile, no identity to carry, no validation) that exists for that case alone and is marked for deletion one release after launch. `report.salvaged` names every page that needed it; it should always be empty.

The server migrates **every blob** once at boot (`migrateSchema` in `server/index.mjs`): Main, the drafts, the `guano-base:*` merge snapshots — whole project copies, so an unmigrated base makes a 3-way merge see every page as changed — and the published baseline. Before the first write it copies the whole store to `data/store.pre-v2/`, because this is one-way. `migrateStoredProject` (`lib/storage.ts`) runs the same function client-side as a defensive no-op, for a blob that arrived some other way (an import, a merge base read straight out of the store).

What the aliases were really offering was a **styled div**, so they live on as insert presets: `PaletteItem.classes` (`lib/elementPalette.ts`) is what an insert lands wearing, and Container/Grid are a `div` with `mx-auto w-full max-w-5xl px-6` / `grid grid-cols-3 gap-6`. A preset carries its own `key` (`paletteKey`), since several entries now share one type and the key is both the row key and what `[data-dock-item]` is queried by.

## Elements, refs and validation (`src/lib/elements.ts`, `src/lib/validateTree.ts`)

Element types live in the `ELEMENTS` registry (`lib/elements.ts`). **A leaf carries text or is void; everything else is a container.** `button`, `link` and `label` are **containers** — an icon, a badge and a label routinely sit inside one — so their words live in a child, and `content` on the element itself is refused. A registry entry's `seed` is the child a brand-new element of that type is created with, so an insert lands something visible rather than an empty box — one builder (`seedChildFor`) for both structure hosts, since both insert into a tree. `icon` is a void leaf rendering an inline `<svg>` from `node.svg` — see Icons below. Leaf-ness is NOT the same question as "does an instance address this as a part": `isInstancePart` is, and it adds the containers an instance has its own say about — `textarea`/`select` (their `name`/`placeholder` are per placement) and `link` (its destination is). Leaf-ness alone made an `input` a part and the `textarea` beside it not one, and left a component's `<a>` unaddressable, which is why a Button component could not be a link. **Capitalized** types (`Card`) are **component instances**, resolved through the component registry (`isComponentType` from `lib/components.ts`) alongside `isKnownElement`, never by name-casing alone.

`node.ref` is the **client ref** — a stable, human-readable address, node state like everything else. It emits **nothing** on the published page (`htmlId` is the separate DOM id; `export.mjs` never sees a ref), and a component master can neither hold one nor emit one (`cloneForMaster` strips it). Refs are page-scope and must be **unique**. They earn their keep twice: agents address by them (`edit_elements` `ref:`/`setRef`, `bind_interaction` `ref`/`targetRef`, `get_page {elements:"refs"}`, `data-ref` in the HTML), and `applyHtml` adopts by them. `useElement.setElementRef` refuses a collision and a ref on the body and returns whether it wrote; a human sets one by renaming a row in the Layers tree, which surfaces the reason. Extraction moves the block's ROOT ref onto the instance wrapper and drops the rest (`useComponents.createComponent`, and `makeComponentFrom` in the MCP tools, which also reports the dropped ones) — a ref inside a component would be duplicated on every instance.

**Validation is `lib/validateTree.ts`**, over the tree, reporting `{nodeId, message}`: a duplicate ref, a ref inside an instance, an unknown collection on a list/item/slider, a misplaced `list-empty`, `@item` inside a data-only collection, an unknown component, and a component containing itself. The grammar half of the old `validateDocument` — indentation, unclosed blocks, leaf-vs-container form, invalid tokens — cannot happen in a tree and is gone. `LayersPane`'s issues footer is where a human sees these and selects the offending node.

## The agent format: HTML (`src/lib/html/`)

Agents read and write pages as a **strict HTML subset** — a format every model already knows, where one write carries structure, classes and text together (the DSL needed a structure call and then a second round of element edits). This is what the MCP tools speak. Nothing in `src/` imports it, so the parser never enters the browser bundle (checked against `dist/`).

- **`tags.ts`** is the registry ↔ HTML mapping, in both directions, and the only place the two are reconciled. Tag names are **case-sensitive**: that is what lets `<Card>` mean a component instance, and why the parser is hand-rolled rather than parse5 (every HTML5 parser lowercases tag names). `ALIAS_OF` makes `container`/`grid` → `div`, `heading` → `h2` and `dropdown` → `select` serialize as their target AND compare equal, so a write never re-mints a node over a difference that renders nowhere. The v2 migration collapsed them in the stored data, and they survive in the registry only as a render fallback for a blob it never saw. `impliedAttrs` is the registry's own (`checkbox` is `<input type="checkbox">`) — part of the element's identity, emitted by the writer and consumed by the reader rather than stored as a custom attribute.
- **`serialize.ts`** is the read: canonical, deterministic, two-space indented, with a fixed attribute order (`data-id`, `data-ref`, `class`, then alphabetical) because the page `version` is a hash of it. A **component instance's interior shows content only** — its classes and shared attributes are the master's, so printing them would invite an edit that lands nowhere; a component READ (`masterToHtml`) shows them, which is where they are editable. It prints a node's OWN values, never what it inherits, so a round-trip can't shadow a master's text. Interactions and animations appear as read-only `data-interactions` / `data-animations` names.
- **`parse.ts`** is lenient in, canonical out: a void tag without the slash, a lowercase `<card>`, comments, numeric entities and a `<div>` of plain text all work; an unknown tag, a mismatched or unclosed tag, a duplicate attribute, an unquoted value, an `on*` handler, a `<script>` and text loose inside a container are refused with `line:col`. Caps at 2 MB and depth 64. A **leaf's inner markup is taken raw** and handed to `sanitizeRich` — rich copy carries `<strong>`/`<a>`/`<br>`, which are not elements of this format.
- **`apply.ts`** is the write, and **the one place node identity is still MATCHED rather than simply kept** — the reason `reconcile` existed. `data-id` (an 8-hex prefix, lengthened on collision; echoing it back is what carries identity), then `data-ref`, then a tree LCS on `type|arg|link`, then by type. The id/ref claims resolve **document-wide and before any LCS**, so one level's guess can never take a node a deeper level addressed by id. **A claim that cannot be honoured is reported, never dropped quietly**: the same id on two elements is REFUSED (document order decided it, so an overlay's close binding silently became a new trigger wrapper's while the response said `kept: 3, refused: []`), a type mismatch warns and falls through to the LCS, and an id matching nothing at all warns — but an id naming a node inside an instance stays silent, because that is the ordinary round-trip. A node inside an instance is deliberately NOT addressable (its structure is the master's; it is a positional part), and a claim that would make a node its own ancestor is refused — a cycle in the tree is unrecoverable.
- **Refusals are never silent**, which is the whole point: a class inside an instance, an attribute that belongs to the component, an unusable `src`, a part count that doesn't match the master — each comes back named, with the tool that *can* do it. `warnings` is the separate list for what landed but is worth saying (a class the Style panel has no control for is **kept**, because every renderer uses `node.classes` verbatim and dropping it would change the published page).
- One **normalization**: a write turns `classes: ""` into no key at all, exactly as the editor's own class writer does.
- The **page `version`** (`pageVersion` in `tools.mjs`) is `sha256` of this HTML plus name/slug/status — so it changes iff something a structure write could clobber changes. Deliberately NOT the `seo` block (its own tool owns it), and not the read-only `data-interactions`/`data-animations` names (`{effects: false}`), because an effect is node state the HTML *reports* but does not *carry*: it survives every write by construction, and a version that moved when a binding changed would be the same spurious `stale-version` the old marker sync caused.

## Rendering (`useRenderNode.ts` + renderers)

`useRenderNode.ts` is the **shared rendering core** used by two renderers: Build's `ElementRenderer.vue` (`components/editor/canvas/`) and Preview's `PreviewRenderer.vue` (`components/site/`). It resolves element type → tag, component master mapping, collection/entry scope (`EntryScope` provide/inject), live interaction firing (hover/click/change via listeners, appear via IntersectionObserver, scrolled via a window listener), and class composition (`node.classes` + interaction classes). Inside a component instance, style/interactions come from the mapped master while content stays the node's own. Content precedence: bound collection field → node's own content → mapped-master content → element default. `server/export.mjs` reimplements this same logic in plain JS to emit static HTML (the only renderer of the published site) — keep the two in sync.

**An empty container gets a box on the Build canvas, and NOWHERE else** (`emptyBox` in `ElementRenderer.vue`, `declaresOwnBox` in `canvas/emptyBox.ts`): `section`/`div`/`header`/`grid` seed no child (only `label`/`button`/`link` do), so a fresh one renders as zero height with no background — invisible, unselectable on the canvas and impossible to drop into, which is the one thing a tree editor must not be. It is given `min-h-10` plus a hairline dashed outline when it is a non-leaf element with **no children, no resolved content, and no class of its own that declares a box** — a height (`h-`/`min-h-`/`size-`/`aspect-`), vertical padding (`p-`/`py-`/`pt-`/`pb-`, which gives an empty box height), or self-placement (`absolute`/`fixed`/`hidden`/`contents`). The test runs on `framedClasses`, the breakpoint-resolved string, so an element sized only at `md:` keeps the box in the mobile frame. It lives in `ElementRenderer`'s `classes` computed beside the selection outline and the drop indicator — editor affordances, like a list's row template being drawn for an empty collection — so **Play and the export never see it** and no published pixel moves; the selection and drop classes carry `!` so they still win. Types with a canvas shape of their own are exempt (`body`, `collection-list`, `collection-item`, `slider`, `custom-code`). Coverage: `e2e/ui-layers.spec.ts` ("an empty container is given a box").

**Binding scope is decided by the TARGET, not the trigger** (`src/lib/shared/entryScope.js`, imported by `useInteraction` and `export.mjs`). An interaction's state key is `interactionId:targetId[@scope]` and an animation's play key is `bindingId[@scope]`, where the scope is the component instance plus — only when the binding's owner and its target share one **entry scope** — the entry. `buildScopeRoots` is the index: a node is in an entry scope when it sits inside a `collection-list`, inside a bound `slider`, or in the template body a `collection-item` embeds. Keyed off the trigger (as it was until this was fixed), a row button that opened the ONE shared sheet outside its list wrote `X@e<row>` while the sheet, rendered once, listened on `X` — the key never matched, the click did nothing, and both `edit_elements` and `publish` reported success. The entry part still earns its keep for per-row effects: without it a hover on one card fires every repeat. Both renderers resolve it per BINDING, which is why the target indexes (`targetIndex`, `animTargetIndex`, `masterBindingIndex`, `buildPlainTargets`) all carry the owner id beside the binding. Regression coverage: `e2e/export-repeat-bindings.spec.ts`.

**A CHANNEL is the one target with no scope at all** (`src/lib/shared/channels.js`, `isChannelTarget` in `shared/interactionKeys.js`). A binding sets `targetId: "@start"` and every element carrying `channel: "start"` listens — wherever in the project it lives. That is the only way ONE modal can be opened from a header component on every route: a node id addresses one tree, and a master's binding keys per instance, so the overlay used to have to live inside whatever opened it (`buildPlainTargets` walks a route's page trees, which is exactly why a master's binding could never reach a page element). Because the trigger and the listener are in different trees, **neither side can attach an instance or an entry scope** — the other could not reproduce it — so `scopeFor` returns `undefined` for a channel target in all three renderers, and an exclusive `group` on a channel binding is unscoped too (which is what lets one group span a page trigger and a master trigger). `buildChannelIndex` is the project-wide index the exporter builds once per export and every listener reads, never "what has rendered so far". `channel` is **shared** state like classes: inside an instance it is the master's, so a mirror cannot override it and an instance wrapper cannot carry one (it emits no element). Tweens on a channel are **`click` only** — a click play is the one tween key shared per (animation, target); every other trigger is keyed per binding, so two of them aimed at one channel would run two timelines on one element. a tween listener is matched by the BINDING key (`els[n].a`), so a channel binding's `k` is unscoped on both sides. `validateTree` refuses a bad name, a second listener in one tree, a listener on any component-typed node (an instance wrapper AND a master ROOT — both emit no element, so the listener's state key would have nowhere to land) and one inside a repeat ("it would open once per row"); `edit_elements {channel}` refuses the master root too, which was the one writer that did not and so published a modal nothing could open while every tool reported success. **What makes a wrapper emit no element is ONE shared predicate** (`isBareWrapper` in `shared/instances.js`), because the exporter's copy ran BEFORE `attrsFor` and silently discarded everything that call would have written — the node's whole `data-fx` entry, its `ctx.fx` and modal registration — and tested a different set of keys from the canvas's (no channel, no animations, no "is anything aimed at this"), which made a root channel work or not depending on whether the root happened to carry a class; `publish` warns `binding-target-unreachable` for a channel nothing published declares and `channel-declared-twice` for a route that declares one twice (two instances of the component that LISTENS — two instances of the component that OPENS one are fine). It is written from three places: `data-channel` in the HTML (a carried attribute, inside the version hash — a page read prints only a node's OWN value, so a component's channel is not echoed inside an instance and writing one there is refused), `edit_elements {channel}` (`""` clears; `bind_interaction`/`bindInteractions` take `channel` as sugar for `targetId: "@name"`), and the Data panel's **Channel** field (`useElement.setElementChannel`, master-aware through `editTarget`, returning whether it wrote like `setElementRef`) beside a **Channel** choice in the trigger's target picker. Coverage: `e2e/export-channel.spec.ts`, `e2e/interactions.spec.ts`, `scripts/check-html.ts`.

## Subsystems: read the doc before editing the subsystem

**The detail lives in `docs/`, one file per theme.** Each entry there records the invariant **and the bug that produced it**, which is the only thing that stops a fix being undone; none of it is re-derivable from the code. READ the file before editing the subsystem — or just its `##` section when you need one answer.

- **`docs/server.md`** — the server-backed store and autosave, drafts and the 3-way merge, auth roles and the contributor/reviewer merges, agent policy, integrations, capabilities, forms, redirects. ## Instance identity (`server/instance.mjs`, `data/instance.json`)

**Which project a port is answering for.** Several Guano projects on one machine all default to 4174, so the port names nothing — whichever instance boots first owns it, and an API token is minted into exactly ONE data dir. A client configured for project A that reaches project B is answered with a **401 indistinguishable from a revoked token**; `guano mcp` exits on it before the MCP handshake, so the only thing the user is ever told is "MCP server not connected" while a valid token sits in a config file pointing at a live, healthy server. Nothing anywhere named the cause. Three pieces close it.

**`id`** is an opaque 32-hex string minted once per data dir and never changed. `/api/health` reports it — which is safe on the one unauthenticated route precisely because it is opaque: no path, no name, nothing derived from a secret, no store parse. The human-readable `name` is served only to an authed caller, on `/api/auth/me`. `guano connect` bakes the id into the client entry as **`GUANO_INSTANCE`**, and `guano mcp` compares it against health **before presenting the token** (`instanceMismatch` in `mcp/server.mjs`), so the wrong project is refused by name — "expected instance b219e658, got 1dadfd6b" — instead of 401ing. An entry written before this existed carries no id, so the bare 401 is also given the sentence it was missing. An older instance reports no `instance` at all and must keep working, which is why a missing field is never a mismatch.

**`port`/`previewPort`** are written **after** `listen` resolves, because the port a project owns is the one it actually got — recording what it asked for would remember a number that was already taken. `boot()` then prefers the remembered port over the 4174 default whenever `PORT` is unset. The record is also why the walk warning can distinguish "something took the default" from "something took MY address", which is the case where a client config has gone stale.

**The config entry is per project**: `connect` writes `mcpServers["guano-<slug>"]`, not the fixed key `guano` it used to — which silently EVICTED the previous project's entry, so connecting a second site disconnected the first with no evidence but Claude no longer reaching a site nobody had touched. A legacy bare `guano` entry is retired only when it is demonstrably the same instance (matching id or url); deleting one that is not would disconnect a project the run never looked at. The slug puts the project in front of the agent too (`mcp__guano-landing__get_page`).

**The data dir is the authority on identity, never the port** (`readIdentity` in `mcp/connect.mjs`). Probing an address first is the same bug one layer up: with no `GUANO_URL` set, `connect` would read health off 4174, find whichever project won it, and bake ANOTHER project's id and address into this project's entry — connecting Claude to the wrong site while reporting success. So it reads `instance.json` first and consults a running server only to confirm it is the same instance (then the live port wins) or to learn an address for a dir with no record yet. An explicit `GUANO_URL`/`PORT` is a contract and still wins.

**`connect` resolves the data dir the way the server that will run does** — an explicit `GUANO_DATA_DIR`, then `<cwd>/data`, then `<cwd>/server/data`, and only then the packaged default — and **pins `GUANO_DATA_DIR`** for every server module it then loads, because `util.mjs` reads it once at import time and `agent-policy.mjs` derives its own file from that. Imported from `packages/guano/`, `util.mjs` resolved to `packages/guano/server/data`, a directory a repo clone's `npm run serve` never reads: the nonce landed there, the server looked in `<repo>/server/data`, and connect died with `nonce mismatch — run guano connect from the instance machine`, which is the one thing that was never wrong. That refusal now names the directory the server actually reads.

**`.env` is loaded by the CLI** (`process.loadEnvFile` in `bin/guano.js`, Node's own, so the zero-dependency rule holds). Nothing read it before, so the `PORT` the scaffolder documented was inert; a real env var still wins, since `loadEnvFile` does not overwrite. `npm create @useguano` now picks a **free port** (stepping by two — a site needs its preview port above it) and writes a real `.env` with it, so a new project's address is an explicit, non-colliding fact in a file the user can read.

Coverage: `e2e/instance-identity.spec.ts` — the stable id, the remembered port reclaimed while the default is still held, the two refusals, and two projects connecting without evicting each other.

## Process lifecycle (`server/lifecycle.mjs`, `server/log.mjs`, `boot()`)

**`boot()` runs before the socket accepts anything**, and that ordering is the
point: the one-way v2 migration used to run inside an `async` listen callback
nobody awaited, so the server was already serving while blobs were rewritten
under it, outside the per-key lock. A throw in `boot()` refuses to start rather
than serving an unmigrated store. The EADDRINUSE port walk lives inside
`listenWalking`'s promise so no retry can re-enter boot, and `BOOT_TIMEOUT_MS`
logs the stalled stage rather than leaving a silent hang.

**SIGTERM drains.** `installShutdown` stops accepting, ends the SSE change feed
(those responses never finish on their own, so `server.close()` would wait out
the whole deadline on connections working exactly as designed), then waits on
in-flight requests and on `withCritical` sections under **two** deadlines —
a request and an export are different obligations, and cutting an export
between its two renames is what leaves no live site at all. Critical sections
are a Set, not a counter, so a slow drain names what it is waiting on. A second
signal exits `128+signum`. A signal during boot lets the current blob finish
(`migrateSchema` is idempotent, so the next boot resumes).

**`GET /api/health`** is the one unauthenticated `/api` route, since a probe
carries no credential — which constrains it: no path, no user count, no secret,
no store parse (`published.json` is hundreds of KB) and no probe file written
(that is the debris the boot sweep exists to clear). 503 only for draining and
an unwritable data dir; an empty store is 200 `degraded`, or a fresh instance
could never come up behind a load balancer.

**Logging goes through `server/log.mjs`** — levels, `LOG_LEVEL`, `LOG_JSON=1`,
and `log.banner` for the startup box (a timestamp in front of an ASCII box is
worse, and under JSON it would be mangled). Every response carries
`x-request-id`, one access line per request at `info`, and both catch-alls put
that id in the body and honour `err.expose`. **Never add a bare `console.*` to
`server/`.**

**The staging primitives live in `server/util.mjs`.** `swapDir` ROLLS BACK: it
renames live aside then staged in, and a failing second rename used to leave no
live directory at all. `withStagingDir` cleans up in a `finally`, which the
export and the package import both lacked — any throw stranded a full copy of
the site forever. `writeAtomic` fsyncs and uses a per-process tmp name (two
writers shared one `${file}.tmp` and the loser's rename ENOENT'd into an empty
catch). `sweepStaleDirs` / `sweepOrphanTmpFiles` collect the debris at boot,
**age-gated at an hour** — two instances CAN share a data dir (the documented
port-walk case), so a young staging dir may belong to a live publish. The base
list is exact: `store.pre-v2` is the only way back from the migration.

**Retention** hangs off one daily timer: form submissions, snapshots (newest N,
floored at 1) and the media variant cache (by **atime** — a cache hit is a
read, so an mtime policy would evict exactly the files every publish uses).
A snapshot above `SNAPSHOT_MAX_BYTES` is refused, because `createZip` builds in
memory. `buildPackage` leaves the variant cache out, and `applyPackage` accepts
it anyway for the backups already on disk — it rejected them outright, so any
instance that had published a resizable raster had unrestorable snapshots.

## Canvas cost (to be folded into docs/rendering.md)

**Canvas cost is per rendered element × frames.** `useMasterBindings.ts` is the per-master index behind `scopedClassesFor` / `scopedTargetStateKeys` / `scopedAnimBindings` — each used to walk the whole master through the reactive proxy, once per element inside an instance, which on a 9,500-element page (three frames of an app screen) was a 3.4 s freeze and 880 MB of heap; `propForBase` in `styles.ts` is memoized for the same reason (`mergeClassLayers` asked it per class of every element with variant overrides). `useRenderNode` creates its appear `IntersectionObserver` only for elements with appear bindings. Measured on the Cocoapp prototype: open-page freeze 3.4 s → 1.2 s, heap 880 → 630 MB; what remains is Vue mount cost (~65 KB of composable state per element) and the browser restyling ~85k DOM nodes per Tailwind rebuild. Rendering inactive breakpoint frames lazily is the next lever. **Per-element questions about shared state are per-id marks, never a comparison against one ref**: `isSelected` / `isHighlighted` / `dropPositionFor` in `useElement` read a `reactive(Set|Map)`, which tracks `has`/`get` per key, so a hover or drag change reaches two elements instead of dirtying a computed in all of them (`highlightedElement?.id === node.id` in every `ElementRenderer` and `LayerRow` cost ~15 ms per Layers-row hover on a 5,000-element page, before any render). The marks are written only through `syncSet` (per-key delete/add — `clear()` notifies every key again) and the detached-scope watcher that mirrors `selectedElementIds`.
