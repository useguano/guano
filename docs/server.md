# Server: the store, drafts, auth, agent policy, integrations, forms, redirects

- **Persistence & storage** (`usePersistence`, `lib/store.ts`, `lib/storage.ts`): storage is **server-backed**, not localStorage. `lib/store.ts` is a synchronous in-memory cache fronting the authed `/api/store` key-value endpoints, flushing writes through a per-key latest-wins queue; `hydrateStore()` must be awaited at boot; a 401 anywhere hard-redirects to `/admin/login`. localStorage survives only for the UI theme preference and a one-time legacy migration. Autosave deep-watches `project`, debounced 500ms. Undo/redo are whole-project JSON snapshots in an in-memory history (cap 50, **not persisted** — lost on reload); Cmd+Z / Cmd+Shift+Z, and they go through the SAME merge-on-save path as an edit — a plain write there reverted whatever another writer had changed since this tab's baseline, while the pill read Saved. A merge during an undo REPLACES `history[pointer]` instead of pushing, because the pointer has already moved back and a push discards the redo arm. **`persist(snapshot, key)` takes its key explicitly**: it used to re-read the active branch after its awaits while `persistMerged` captured it before them, so a save in flight across a branch switch wrote the outgoing branch's bytes under the incoming key. The baseline is tagged with its key for the same reason, and advances only when the store reports that write ACCEPTED (a per-key sequence, since the queue drops superseded ops and a superseded op has no honest resolution). `resetTo` is gone, split in two: **`adoptRemote(next)`** takes fresh history and writes NOTHING (the live agent sync, and opening a branch — those bytes came out of that key a moment ago), while **`commitReplacement(next, priorBaseline)`** writes a state that exists nowhere yet (a resolved merge into Main) merge-aware against the Main it was computed from, returning what was actually stored. Storage keys are **branch-scoped** (`guano-project:<branchId>`). A `PUT /api/store/:key` may carry **`If-Match`** (the sha256 of the bytes the caller read): the server compares it under a **per-key lock** and answers 412 rather than overwriting someone else's write. The browser keeps its last-writer-wins autosave by sending no header; the MCP server sends it on every project write, because it reads the WHOLE blob, works for as long as a tool takes, and writes it all back — so what a lost update costs there is not a field but every page the other writer had (`e2e/store-concurrency.spec.ts`).

- **Branches & merge** (`useBranches`, `lib/merge.ts`): surfaced in the UI as **Drafts** (create draft / apply to site / discard) — internal names keep `branch`. Each branch is a full project copy in its own key, plus a `guano-base:<id>` snapshot captured at creation for 3-way merge; `mergeIntoMain(..., { keep: true })` preserves the draft and rebases its base onto the merged Main. `computeMerge(base, main, branch)` is a pure per-item merge (pages/components/collections/interactions/animations/**effects** share one id-keyed helper — a new top-level list has to be added there AND to `summarizeChanges`, or one side's is silently dropped by the `...mine` spread and a draft that only touched it reads as unchanged; breakpoints, the locale pack, and settings each merge as a unit); **every conflict defaults to Main's side** until the user resolves it. **Comments are the one list that unions instead of conflicting** (`mergeComments`): they are review feedback, so both sides' threads come through and replies union by id, with a deletion still meaning a deletion. They used to not merge at all — `comments: mine.comments`, then `mergeIntoMain` overrode it with the ACTIVE session's list, so applying a draft destroyed whichever side the person was not sitting on. A branch SWITCH has no base to compare against and so unions two-way (`unionComments`), erring towards keeping; the real fix is to move comments out of the project blob into a key of their own, so "shared across branches" stops being a copy made on every switch.

- **Users / auth** (`useAuth`, `useUsers`, `server/auth.mjs`): roles `admin | editor | contributor | reviewer`; `canBuild` = admin|editor (`isBuildRole` in `server/auth.mjs` — every "may this account build" gate on the server reads it rather than naming the roles it is NOT, so a role added later is refused by default); `canEditContent` = everyone but a reviewer. **A reviewer reads and comments, nothing else**: their project write goes through `mergeReviewerProject` (`server/contributor-merge.mjs`), which keeps the stored blob whole and takes only `comments`, and is refused outright for a key with nothing stored (they hold no drafts) and for `guano-branches`; publish and preview by any method, tokens, the team list, every store DELETE and every media mutation are 403. Client-side they are pinned to Play like a contributor, `usePreviewEditing.contentEditing` is `!canBuild && canEditContent` so no inline edit is offered, the settings rail has no panels and no publish button, the Pages drawer keeps navigation but loses every create/settings/duplicate/delete affordance and the locale add/delete, and the project settings modal opens on the account section alone. Coverage: `e2e/store-reviewer-code-zip.spec.ts`. scrypt-hashed passwords with **per-record cost parameters** (`kdf` on the user record and on `cfg.site`; absent means the library defaults the hash was made with, so raising the cost cannot invalidate an existing password, and a legacy record is rehashed on its owner's next sign-in), passwords capped at 256 characters rather than silently truncated, HttpOnly session cookie, single-use hashed invite tokens (accepted at `/admin/invite/:token`). The server hard-gates publish (admin/editor only for non-server methods), user management (admin only), and contributor DELETE of project keys (own drafts + `guano-base:*` only). **The contributor build/structure restriction is now server-enforced, not UI-only:** a contributor project write (`PUT /api/store/guano-project:*`) and publish (`POST /api/published`) go through a **server-authoritative content merge** (`server/contributor-merge.mjs`) — the server keeps all structure and `settings` from the stored blob (Main for a new draft) and applies only a content allowlist from the contributor's blob (node `content`/`src`/`background`/`locales`, page/entry `seo`+`status`, collection `entries` full-CRUD, `comments`; rich content and media URLs re-sanitized through `SAFE_SRC`). Structural edits are silently dropped, but a write that would change **custom code or the publish target is refused with a 403** naming the field (a silent drop reads as success, so nobody learns something tried). Complementarily, `GET /api/store` redacts `settings.smtp`/`settings.integrations` for contributors (S4). All of this applies to `guano-base:*` merge-base snapshots too — they are full project copies, so they carry the same secrets and the same structural authority. Store **writes are limited to the keys the product uses** (`guano-project:*`, `guano-base:*`, `guano-branches`, `guano-published-baseline`, `guano-published-info`): the character regex constrained a key's shape, never its name, so any well-formed name could be created and written verbatim — which is how a contributor reached `guano-branches`, the blob carrying the `createdBy` stamp that `ownsDraft` trusts, and deleted other people's drafts. A contributor's write to that blob now goes through `mergeBranchesMeta`, which takes any entry owned by someone else from the stored copy verbatim and REFUSES BY NAME an attempt to change or drop one (a silent revert reads as success). DELETE runs inside the same per-key lock as PUT. Keys **may not contain `_`**: keys map to filenames by `:` → `__`, so an underscore makes that mapping ambiguous and `guano-project__main` would hit Main's file while sliding past every `startsWith('guano-project:')` guard. Draft ownership is the `createdBy` stamp in the `guano-branches` meta (written by `useBranches.createBranch` and MCP `set_target {createDraft}`); contributors may only DELETE drafts they own, with unstamped legacy drafts staying shared. Regression coverage is `e2e/store-agent-security.spec.ts` (server authz over HTTP) and `e2e/mcp-tools-security.spec.ts` (toolset behaviour, in-process).

- **Agent policy** (`server/agent-policy.mjs`, `GET/PUT /api/agent-policy`): `set_target` puts the Main-vs-draft choice in front of the human via **MCP elicitation** when the client supports it (Claude Desktop) — a real dialog whose answer is the consent; only on clients without elicitation does it fall back to the agent-asserted `chosenByUser`/`acknowledgeMain` booleans. Those attestations — and `forcePurge` — are values the **agent itself** passes, so a prompt-injected agent can set them all, and even the dialog rides through the client rather than an authed channel. The real boundary is server-side and keys off how the request authenticated — `isAgentRequest` (a `guano_` bearer, no session cookie; mirrors `requestUser`'s precedence). Four switches, **all off by default**: `allowMainWrites` (write/delete `guano-project:main`), `allowPublish` (`POST /api/published`), `allowCustomCode` (any change to `settings.customCode` or a page's `customCode` — raw `<script>` on every published page), and `allowFormSubmissions` (READ form submissions — site visitors' names and messages, which an injected agent could exfiltrate through any write it can make; no switch ever allows deleting one). Changing `settings.publishing` from a token is refused outright, policy or not. The endpoint is **admin + session-cookie only**: a token able to flip these would guard nothing. With the defaults an agent works in a draft, cannot publish, and cannot ship script — so a successful injection costs a bad draft a human reviews, not the live site. **The switches are edited in Settings → MCP → Agent permissions** (an admin-only `SettingsGroup` beside the token list), and the two that every connected instance needs answered — `allowMainWrites` and `allowPublish` — are ALSO asked at the two onboarding moments, through `onboardingPolicy` (only those two keys, only booleans): the first-run **setup form** (`SetupView`'s "AI agents" section, sent as `agentPolicy` on `POST /api/auth/setup`, applied after `createFirstAdmin` succeeds — creating the first admin is already the trusted moment) and **`guano connect`** (`--main` / `--publish`, or two readline questions defaulting to No; `--yes` skips them and leaves the policy alone; sent as `policy` on the nonce-trusted, loopback-only `POST /api/auth/connect`, which answers with the resulting `agentPolicy`, or written straight through `agent-policy.mjs` when the server is down). When Main ends up allowed, `connect` writes `GUANO_MCP_TARGET=main` into the client config so the agent never asks for a target. **Both happen BEFORE the server has ever run, too**: `npm create @useguano` asks "connect Claude Desktop?" plus the two questions and runs `guano connect --offline` through the just-installed package, which mints a **pending** API token (`userId: null, pendingFirstAdmin: true` in `api-tokens.json` — `apiTokenUser` refuses it, `listApiTokens` lists it under nobody) and writes `agent-policy.json` into `<dir>/data`; `createFirstAdmin` calls `bindPendingTokens`, so the first admin owns it the moment the account exists, and `GET /api/auth/me` in the needs-setup state returns the preset `agentPolicy` (`agentPolicyPreset`, i.e. the file exists) so `SetupView` shows the answers instead of asking again (`useAuth.presetAgentPolicy`, and `setup()` then sends no `agentPolicy`). `--offline` exists because a server on the default port may be ANOTHER project's, and minting through it would connect Claude to the wrong instance. Coverage: `e2e/auth-pending-token.spec.ts`. Settings is where they change afterwards, and the reason every refusal names that exact path: they used to say "enable agent Main writes in Settings" when Settings held no such control, so the only way to allow anything was hand-editing `agent-policy.json` in the data dir — and since a fresh instance has no such file, every agent was permanently unable to touch Main with nothing in the product to change it. `GET /api/auth/me` reports the policy as `agentPolicy` **to a token only** (writing it stays admin + session), so `get_status` carries `permissions` plus a `mainWritesNote` and `set_target` marks a Main target `mainWritesDisabled` with the sentence to read out — the refusal arrives when the target is chosen instead of as a 403 on the first save after an hour of work. A Main target is still ACCEPTED when the switch is off, because refusing it would leave a client configured with `GUANO_MCP_TARGET="main"` no target at all, and so no possible write anywhere.

- **Integrations** (`server/integrations.mjs`, `src/lib/shared/integrations.js`, `GET/POST/PUT/DELETE /api/integrations`): an integration is a **named set of keys** the user creates — not one fixed group per provider — so a site can wire up anything (`SMTP {HOST PORT USER PASSWORD FROM}`, `Zapier {FORWARD_URL}`, `Stripe {PUBLISHABLE_KEY SECRET_KEY}`). A key is **secret** (write-once, masked, never returned) or **plain** (readable, and substituted into custom code). **The WHOLE integration lives server-side** in `server/data/integrations.json`, not just its secrets: while `settings.smtp.host` sat in the project blob and only the password sat server-side, anyone who could write that blob — an editor, a draft, a 3-way merge, a contributor, an agent token — could point the host at their own machine and read the password off the first `AUTH`. `ProjectSettings.smtp`/`.integrations` are deprecated optionals that `migrateIntegrations` carries across once at boot and then **deletes from every blob**. **Reads** are session OR a `guano_` token at admin/editor (an agent needs the key NAMES to write a valid `{{ENV.X}}` reference; `publicIntegration` has no branch that can include a secret value); **writes** are admin + session cookie only, like `/api/agent-policy`. A stored secret can never be flipped to plain — delete and re-add. `envName` (shared) is the one spelling of `<INTEGRATION>_<KEY>`, used by the panel, the exporter and the MCP listing; two names that normalize to the same prefix are refused at write. The exporter substitutes `{{ENV.…}}` in **custom code only** (never node content, which is user data) and **fails the export** on a reference to a secret or unknown key — a warning would ship the page.

- **Capabilities** (`server/capabilities.mjs`): the server does not know which integration "is SMTP". A capability declares the keys it `needs`, an admin **picks** an integration for it (Settings → Forms), and `resolveCapability` validates the pick and returns the key bag; a missing key is refused **by name** ("Postmark is missing PORT"), at pick time and at send time, with the same message. `verifyCapabilityPick` is the stricter pick-time check — for `webhook` it also resolves the URL through `net-guard.mjs`, so one aimed at the operator's LAN is refused while the admin is still in the dialog. `smtp`'s HOST allows a **single label** (`localhost`, a compose service name): requiring a dot rejected exactly the self-hosted local-relay case. `server/smtp.mjs` is a zero-dependency client (the `zip.mjs` precedent): AUTH never in plaintext (STARTTLS required off 465, torn down rather than falling back), certificate verification on and checked against the real host (omit `host` on the upgrade and node checks the cert against the literal "localhost"), every header value **throws** on CR/LF/NUL, body dot-stuffed.

- **Forms** (`src/lib/shared/forms.js`, `node.form`, `server/public/*`): a `form` is plain until `form.enabled`, then it posts to **`POST /_guano/forms/:id`** — the only unauthenticated write in the product. A form that is NOT enabled exports `method="dialog"` plus `data-form-inert`, because a bare `<form>` still submits natively — Enter in a text field, or any `<button>` with no `type`, GETs the current route with every named control in the query string, which on a questionnaire puts the answers in the address bar, in history and in the host's logs. The dialog method is abandoned by the browser after constraint validation, so nothing is sent and native validation survives; both Vue renderers already `preventDefault`, which is what kept this invisible until the published page. `publish` warns (`form-not-enabled-has-fields`) when such a form holds named controls. It lives **outside `/api`** (every mutating `/api` route is cookie-authed and same-origin-checked; one loosened guard must not expose both) in the namespace the site-password unlock already owns, which is also why the preview server can serve its twin. It validates against the **manifest written at publish** (`forms-manifest.json`, never inside `site/`), not the live project and never the request: the visitor submitted the page that SHIPPED. Refusal order is cheapest-first — CORS, id shape, rate limits, manifest, content type, 32 KB body, honeypot/`_t` (answered as **success**, so a bot learns nothing), `_route`/`_entry` against what was exported, then the field allowlist. `node.form` says only *whether* it notifies: recipients, the mailer and the webhook are admin-only server state (`publish.json` → `forms`), because a recipient field in the blob would let a draft, a merge or an injected agent redirect other people's leads. It is outside the contributor content allowlist. `form-success`/`form-error` are **elements** (the `list-empty` precedent) emitted hidden; `validateTree` reports a misplaced or duplicated one and a nested form. Submissions are JSONL per form, 0600, no IP and no user agent, capped (20 MB / 10 000 → `503`), pruned on `forms.retentionDays`. Reads are admin/editor; an agent token needs `allowFormSubmissions` (off by default) and gets every value **fenced**; nothing deletes with a token. CSV quotes per RFC 4180 and prefixes `= + - @ TAB CR` with `'` — visitors write those cells and a spreadsheet executes them. A site published as zip/GitHub reaches the instance through `settings.publishing.apiOrigin`, which agents and contributors already cannot write.

- **Redirects** (`settings.redirects`, `src/lib/shared/redirects.js`): 301s, `{id, from, to}`. **The invariant is that a redirect can never cost a PAGE**: `resolveRedirects` runs at EXPORT time against the routes that actually shipped (`written`, the authoritative list), so a rule whose source is a real route is dropped and reported instead of served — which is what lets the server answer a redirect BEFORE it looks for a file (`serveSiteDir`), i.e. a real 301 rather than the meta-refresh stub. The stubs are written anyway, because `site/` IS what the zip ships and a static host cannot answer a 301 of its own; the `server` method never reads them. A chain is collapsed to one hop and **stops at a published route** (following it past a live page was the one outcome a redirect must never produce), a source with no locale prefix gets a per-locale twin (a slug is shared across locales, so a rename would otherwise break every translated route), and `from: '/'` is refused. Served from **`data/redirects.json`** (written after a successful export, like `forms-manifest.json` — answering a redirect must not parse `published.json`), read through `manifestReader`, whose 5s cache a publish now **invalidates** (`read.invalidate`) — without it the live site kept answering the previous publish's rules for five seconds, which is exactly the moment someone is watching. The 301 carries `cache-control: no-cache` deliberately: a bare 301 is cached by browsers indefinitely, so removing a rule later would leave every visitor who followed it permanently stuck. In the editor: Settings → Site → **Redirects**, plus the two prompts that make it a feature rather than a list nobody opens — `PageSettingsEditor` offers the 301 when a slug changes (from the path the item had before the first change of this session, so /a → /b → /c offers /a) and reports when the current path is itself a redirect source. **Both alerts can be true at once** and are independent, because renaming back onto an old path asks two different questions. Their per-id marks are `reactive(Map|Set)`, not plain ones: `redirectOffer` early-returns before touching `page.path`, so a plain Map read was never a dependency and the computed stayed on the `null` it returned at mount (the `useElement` selection-marks rule again). MCP: `update_page {redirect: true}` (else `redirectSuggestion`), `update_settings {redirects|addRedirects|removeRedirects}`, `get_settings.redirects`, and the `redirect-shadowed` / `redirect-dangling` / `redirect-chained` publish warnings — computed in `collectPublishWarnings` off the route table the dead-link check already builds, NOT off the export stats, because the in-process harness stubs publish and a warning nobody can test is a warning that rots. Coverage: `e2e/store-redirects.spec.ts` (the served 301), `e2e/ui-redirects.spec.ts` (both prompts), `e2e/mcp-tool-contracts.spec.ts`.
