## Persistence & storage

`usePersistence`, `lib/store.ts`, `lib/storage.ts` — storage is **server-backed**, not localStorage. `lib/store.ts` is a synchronous in-memory cache fronting the authed `/api/store` key-value endpoints, flushing writes through a per-key latest-wins queue; `hydrateStore()` must be awaited at boot; a 401 anywhere hard-redirects to `/admin/login`. localStorage survives only for the editor's own light/dark chrome preference (`guano-editor-theme`). Autosave deep-watches `project`, debounced 500ms. Undo/redo are whole-project JSON snapshots in an in-memory history (cap 50, **not persisted** — lost on reload); Cmd+Z / Cmd+Shift+Z, and they go through the SAME merge-on-save path as an edit — a plain write there reverted whatever another writer had changed since this tab's baseline, while the pill read Saved. A merge during an undo REPLACES `history[pointer]` instead of pushing, because the pointer has already moved back and a push discards the redo arm. **`persist(snapshot, key)` takes its key explicitly**: it used to re-read the active branch after its awaits while `persistMerged` captured it before them, so a save in flight across a branch switch wrote the outgoing branch's bytes under the incoming key. The baseline is tagged with its key for the same reason, and advances only when the store reports that write ACCEPTED (a per-key sequence, since the queue drops superseded ops and a superseded op has no honest resolution). `resetTo` is gone, split in two: **`adoptRemote(next)`** takes fresh history and writes NOTHING (the live agent sync, and opening a branch — those bytes came out of that key a moment ago), while **`commitReplacement(next, priorBaseline)`** writes a state that exists nowhere yet (a resolved merge into Main) merge-aware against the Main it was computed from, returning what was actually stored. Storage keys are **branch-scoped** (`guano-project:<branchId>`). A `PUT /api/store/:key` may carry **`If-Match`** (the sha256 of the bytes the caller read): the server compares it under a **per-key lock** and answers 412 rather than overwriting someone else's write. The browser keeps its last-writer-wins autosave by sending no header; the MCP server sends it on every project write, because it reads the WHOLE blob, works for as long as a tool takes, and writes it all back — so what a lost update costs there is not a field but every page the other writer had (`e2e/store-concurrency.spec.ts`).

## Branches & merge

`useBranches`, `lib/merge.ts` — surfaced in the UI as **Drafts** (create draft / apply to site / discard) — internal names keep `branch`. Each branch is a full project copy in its own key, plus a `guano-base:<id>` snapshot captured at creation for 3-way merge; `mergeIntoMain(..., { keep: true })` preserves the draft and rebases its base onto the merged Main. `computeMerge(base, main, branch)` is a pure per-item merge (pages/components/collections/interactions/animations/**effects** share one id-keyed helper — a new top-level list has to be added there AND to `summarizeChanges`, or one side's is silently dropped by the `...mine` spread and a draft that only touched it reads as unchanged; breakpoints, the locale pack, and settings each merge as a unit); **every conflict defaults to Main's side** until the user resolves it. **Comments are the one list that unions instead of conflicting** (`mergeComments`): they are review feedback, so both sides' threads come through and replies union by id, with a deletion still meaning a deletion. They used to not merge at all — `comments: mine.comments`, then `mergeIntoMain` overrode it with the ACTIVE session's list, so applying a draft destroyed whichever side the person was not sitting on. A branch SWITCH has no base to compare against and so unions two-way (`unionComments`), erring towards keeping; the real fix is to move comments out of the project blob into a key of their own, so "shared across branches" stops being a copy made on every switch.

## Users / auth

**The first account needs a setup code from anywhere but this machine.** `POST /api/auth/setup` was gated on `needsSetup()` — no users exist — and nothing else, while **the server binds every interface**: on café wifi, or on a VPS in the minutes before its owner first opens `/admin`, the first stranger to reach it became the instance's admin. `createFirstAdmin` → `bindPendingTokens` makes that worse than it sounds, because they also inherit every token `guano connect --offline` and the scaffolder minted; and a data-dir wipe reopens the window on a machine that was set up months ago, which is a thing people do. It was reachable from a malicious WEB PAGE too: the same-origin check compares `Origin` to the `Host` header, which is exactly what a DNS rebind satisfies.

**Loopback stays free**, because that is the launcher, `npm run dev` and whoever is at the machine's own keyboard — all of them already holding the data dir, which is the ownership `/api/auth/connect` and `launcher-session` trust too. Those three now share one `isLoopbackSocket(req)`, reading `req.socket.remoteAddress` and never `clientIp(req)`, so no header can claim loopback. From any other address the body must carry `setupCode`: 16 bytes minted in `boot()` **before the socket opens**, kept at `<data>/setup-code` (0600, through `writeAtomic`), printed in the first-run banner where only the operator can read it, compared with `timingSafeEqualStr`, rate-limited 10/15min per address, and deleted by `createFirstAdmin` — single-use by construction, since the account it guards can only be created once. `GET /api/auth/me` answers `setupCodeRequired` so `SetupView` asks for it exactly where it is needed, and a headless VPS install still works. Setup also reads its body with `MAX_AUTH_BODY` now rather than the 10 MB default. Coverage: `e2e/auth-setup-code.spec.ts`.

**The desktop launcher signs itself in.** `POST /api/auth/launcher-session` mints a session for the instance's owner (`oldestAdmin()` — one instance has one owner, and a second admin added later must never take the app's seat) with no password, on the same trust `/api/auth/connect` already extends: the launcher spawned this process and holds the data dir. Three gates, and the first is what keeps every ordinary deploy untouched: the route **does not exist** unless `GUANO_LAUNCHER_SECRET` is in the environment (the app generates 32 bytes per start and passes them at spawn — never on disk, dead with the process); it reads `req.socket.remoteAddress` directly rather than `clientIp(req)`, because `clientIp` honours `X-Forwarded-For` under `TRUST_PROXY` and a header must not be able to claim loopback; and the secret is compared with `timingSafeEqualStr`. No rate limiter: loopback plus 256 bits is the limiter. Unlike connect's nonce the secret is REUSABLE, because the app re-mints on every 401 — expiry, or a password changed in a browser — which is the whole point: a desktop window must not land on a login screen for a project the person started from their own Dock. Before setup it answers **409 `needsSetup`**, not an error, because the launcher's response is to show the webview and let setup happen. Its cookie alone is minted **without `Secure`**: it is loopback-only by construction and the app writes it into WebKit's store itself rather than taking it off a response, which removes the one thing that could silently fail to be sent. **The server binds all interfaces** (`srv.listen(attempt)`, no host), so none of this may weaken auth — a LAN visitor still logs in.

**`via` on the session record says how it was minted**, and `GET /api/auth/me` reports it as `host: 'launcher' | 'browser'` so the editor can hide the chrome the app's own window already provides (→ `docs/ui.md`). It rides on the SESSION rather than a second cookie: nothing a page can forge, and the tag lives exactly as long as the thing it describes. `/api/auth/update` must read `sessionVia(req)` **before** `destroyUserSessions` — the password branch revokes every session and re-issues one for the caller, and reading after would always see null, silently handing a desktop window browser chrome on the next password change. The SPA's half is `src/lib/hostBridge.ts`; two of its bounces are invisible to WebKit's navigation delegate (the router guard's `replaceState` to `/login`, and `/admin/setup` never being a main-frame navigation), which is why the re-mint lives in the router guard rather than only in Swift. Coverage: `e2e/auth-launcher-session.spec.ts`.

**Builder sessions: a browser session is never a builder session.** Decided 2026-10-18 — the Build surface (structure, settings, custom code, integrations, publish, invites) is reachable only from the desktop launcher, and a deployed instance serves Play to contributors and reviewers in a browser. The protection is at the **API**, not in hidden UI: `effectiveRole(req, user)` in `server/auth.mjs` answers the account's own role when the request is a **builder request** — `sessionVia(req) === 'launcher'`, or an agent bearer, which keeps its own gate in the agent policy — and `min(role, 'contributor')` otherwise, so an admin signed in at `https://site/admin` in Safari is a contributor at every gate: their project write is content-merged, custom code and the publish target are refused by name, and users, invites, tokens, publish, snapshots and project import/export are 403. **The cap is applied ONCE, where the request's user is resolved**, rather than at each of the twenty-odd role checks downstream: `requestUser` and `sessionUser` in `server/index.mjs` return the live record with `role` replaced by `effectiveRole(req, user)`, so every gate that already read `user.role` — `isBuildRole`, `=== 'admin'`, the contributor and reviewer branches of the store write, the publish method checks — is correct without being touched, and a route written tomorrow is covered by default. Twenty independent judgements would have meant a straggler, and a straggler is a hole; the sentence lives beside `isBuildRole` where someone editing a gate will read it. `sessionUser` deliberately **shadows** the import of the same name, and the two places that need the ACCOUNT's own role name `requestAccount` / `sessionAccount` and say why: `GET /api/auth/me`, which reports both, and **approving a device authorization**, which is the one action whose proof of authority IS a browser session — a human signed in to this instance's own `/admin`. Cap that one and nobody could ever approve anything, the desktop app's own launcher token included, because that approval is where the token comes from. A contributor's CONTENT publish still works for a browser session, because that is exactly what "capped at contributor" means. `GET /api/auth/me` reports `role` (the account's), `effectiveRole` and a server-computed `canBuild`, so the SPA has ONE source for the answer and pins itself to Play with no new client logic (`useViewMode` already watches `canBuild`). **A test that only checks the UI tests nothing** — the coverage is over HTTP, in `e2e/store-agent-security.spec.ts`. The one sentence the SPA adds is for the admin who opens their own VPS in a browser and reads their site as read-only: *"You are signed in from a browser. Building happens in Guano Launcher."* — without it that is a bug report.

**The token kinds are a PREFIX, because a field is a check someone can forget.** A launcher token is `guanol_…`, an agent token stays `guano_…`, and they are different TYPES to every parser: `requestUser` matches `Bearer guano_` and nothing else, so a launcher token cannot *resolve* as an agent bearer — not "is refused", cannot be read — and the session exchange parses `guanol_` alone. Only two sites parse the prefix (`requestUser` here, `whoami` in `packages/guano/mcp/server.mjs`). The record also carries `kind` so `GET /api/tokens` can tell an admin which is which, but the prefix is the enforcement. **The hole this closes:** agents are gated by the agent policy (`allowMainWrites`, `allowPublish`) because they are judged *by how they authenticated* — so if the exchange accepted any `guano_` token, an injected agent would trade its token for a cookie, stop being an agent in the server's eyes, and write Main with the policy off. Each door still refuses the other **by name**, so the attempt is visible rather than merely unsuccessful: *"an agent token cannot open the editor"*, and the MCP server's boot `whoami` names a launcher-kind token the same way. A launcher token is minted only by the device flow when the request says `kind: 'launcher'`, and the consent screen says which sentence it is approving — *"Guano Launcher on this Mac wants builder access"* is not *"Claude wants to work on this site"*. **Who may approve which kind differs, and admin-only for a launcher was a dead end rather than a safeguard:** an agent token is instance-wide authority governed by the agent policy, so it stays admin-only; a launcher token carries exactly the approver's OWN role, so a build role is the right bar — and without that an editor with their own Mac could not be authorized at all, since the token is minted for whoever approved it and an admin approving an editor's launcher would hand that Mac the admin's authority. A contributor is refused even the consent screen, so a code left on somebody's terminal is not something they can act on; denying stays open to any signed-in account, because saying no can only reduce access. That is also the only way a SECOND builder gets a session at all: the secret proof mints for `oldestAdmin()` alone, so an editor's builder session is a `guanol_` token they approved for themselves. Coverage is one named test that exists before the gates flip and never goes away: **"an agent token cannot open the editor, and a launcher token cannot drive the MCP"** in `e2e/store-agent-security.spec.ts` — mint one of each, present each to the other's door, both 403 by name.

**`POST /api/auth/launcher-session` learns a second proof, and nothing else mints `via: 'launcher'`.** The first proof is unchanged and still loopback-only: `GUANO_LAUNCHER_SECRET` from the spawn environment, which only a server the app started can have. The second is `Authorization: Bearer guanol_…` over `https:` — plain `http:` for localhost alone, exactly as `connect --url` already rules — whose owner holds a build role, which mints that user's session with `via: 'launcher'`. Two proofs of one claim, *I am this person's launcher, for this instance*, and one kind of session at the end of both. The checks run in this order, and the order is the point: https-or-localhost → a `guanol_` bearer is present (**a `guano_` bearer is 403 by name** rather than falling through as unrecognised) → the token resolves → the owner builds → the rate limit. Rate-limited per address like setup, since unlike the secret proof this one is reachable from anywhere. The e2e suite's **one** `openEditor` fixture (`e2e/fixtures/session.ts`) mints through the secret proof over the suite server's loopback, which is why `playwright.config.ts` now puts `GUANO_LAUNCHER_SECRET` in `webServer.env`; `openEditorInBrowser` keeps the form login for the specs where the browser IS the point. That fixture moved **before** the gates flipped, not with them: thirteen specs each carried their own copy of `openEditor` logging in through the form, every one of which becomes a contributor session the moment the gates read `effectiveRole` — consolidating first and proving the suite green turned one big uncertain commit into two small ones. Coverage: `e2e/auth-launcher-session.spec.ts`.

`useAuth`, `useUsers`, `server/auth.mjs` — roles `admin | editor | contributor | reviewer`; `canBuild` = admin|editor (`isBuildRole` in `server/auth.mjs` — every "may this account build" gate on the server reads it rather than naming the roles it is NOT, so a role added later is refused by default); `canEditContent` = everyone but a reviewer. **A reviewer reads and comments, nothing else**: their project write goes through `mergeReviewerProject` (`server/contributor-merge.mjs`), which keeps the stored blob whole and takes only `comments`, and is refused outright for a key with nothing stored (they hold no drafts) and for `guano-branches`; publish and preview by any method, tokens, the team list, every store DELETE and every media mutation are 403. Client-side they are pinned to Play like a contributor, `usePreviewEditing.contentEditing` is `!canBuild && canEditContent` so no inline edit is offered, the settings rail has no panels and no publish button, the Pages drawer keeps navigation but loses every create/settings/duplicate/delete affordance and the locale add/delete, and the project settings modal opens on the account section alone. Coverage: `e2e/store-reviewer-code-zip.spec.ts`. scrypt-hashed passwords with **per-record cost parameters** (`kdf` on the user record and on `cfg.site`; absent means the library defaults the hash was made with, so raising the cost cannot invalidate an existing password, and a legacy record is rehashed on its owner's next sign-in), passwords capped at 256 characters rather than silently truncated, HttpOnly session cookie, single-use hashed invite tokens (accepted at `/admin/invite/:token`). The server hard-gates publish (admin/editor only for non-server methods, **github admin-only**), user management (admin only), and contributor DELETE of project keys (own drafts + `guano-base:*` only). **The publish TARGET is admin-only too, and that now includes editors:** `protectedWriteDenial` returned `null` for every build role, so while `handlePublishConfig` correctly refused an editor the GitHub token, nothing stopped them rewriting `settings.publishing.github.repo` in Main — which is where `handlePost` reads the destination from — and aiming the operator's PAT at any repository it could write. `pushSiteToGitHub` builds a tree with **no `base_tree`**, so that push replaces the branch root: every file not in the export is deleted. An editor is refused the `publishing` delta by name and the `github` method outright; custom code stays theirs. Coverage: `e2e/store-agent-security.spec.ts`. **The contributor build/structure restriction is now server-enforced, not UI-only:** a contributor project write (`PUT /api/store/guano-project:*`) and publish (`POST /api/published`) go through a **server-authoritative content merge** (`server/contributor-merge.mjs`) — the server keeps all structure and `settings` from the stored blob (Main for a new draft) and applies only a content allowlist from the contributor's blob (node `content`/`src`/`background`/`locales`, page/entry `seo`+`status`, collection `entries` full-CRUD, `comments`; rich content and media URLs re-sanitized through `SAFE_SRC`). Structural edits are silently dropped, but a write that would change **custom code or the publish target is refused with a 403** naming the field (a silent drop reads as success, so nobody learns something tried). Complementarily, `GET /api/store` redacts `settings.smtp`/`settings.integrations` for contributors (S4). All of this applies to `guano-base:*` merge-base snapshots too — they are full project copies, so they carry the same secrets and the same structural authority. Store **writes are limited to the keys the product uses** (`guano-project:*`, `guano-base:*`, `guano-branches`, `guano-published-baseline`, `guano-published-info`): the character regex constrained a key's shape, never its name, so any well-formed name could be created and written verbatim — which is how a contributor reached `guano-branches`, the blob carrying the `createdBy` stamp that `ownsDraft` trusts, and deleted other people's drafts. A contributor's write to that blob now goes through `mergeBranchesMeta`, which takes any entry owned by someone else from the stored copy verbatim and REFUSES BY NAME an attempt to change or drop one (a silent revert reads as success). DELETE runs inside the same per-key lock as PUT. Keys **may not contain `_`**: keys map to filenames by `:` → `__`, so an underscore makes that mapping ambiguous and `guano-project__main` would hit Main's file while sliding past every `startsWith('guano-project:')` guard. Draft ownership is the `createdBy` stamp in the `guano-branches` meta (written by `useBranches.createBranch` and MCP `set_target {createDraft}`); contributors may only DELETE drafts they own, with unstamped legacy drafts staying shared. Regression coverage is `e2e/store-agent-security.spec.ts` (server authz over HTTP) and `e2e/mcp-tools-security.spec.ts` (toolset behaviour, in-process).

**`/api/users/members` reports each account's `lastSeenAt`**, because `expiresAt` answers a different question: it is thirty days out, so a session nobody has touched since last month looks identical to one in use. `getSession` stamps it, throttled at a minute like a token's `lastUsedAt` — every authed request would otherwise fsync `sessions.json` — and `lastSeenByUser` folds sessions by USER, since two tabs are one person. `null` means no live session at all, which a caller can tell apart from "a while ago". The one caller is the launcher's **Bring back to this Mac**, which refuses while somebody else has been working in the last ten minutes: a move is not a sync, so their window would simply stop with nothing anywhere telling them why. The view stays editor+ and still carries no ids — `lastSeenAt` is not one.

**Smaller refusals in the same area, each with the hole it closed.** The **device pool** is capped per address as well as globally: the start endpoint is unauthenticated, so two hosts could hold all twelve slots indefinitely and every real `guano connect --url` got a 429 — and the consent screen shows the requesting ADDRESS beside the requester's chosen `name`, which is a label and never evidence. **Approve validates the code before minting**: `createApiToken` ran first and `approveDevice` could still answer "expired", leaving a live hashed record in `api-tokens.json` that counted against the 25-token cap and appeared in the admin's list as an entry nobody could explain. **A display name is capped at 100** in `createUser`/`updateUser`/`createInvite` — `/api/auth/update` takes one from any role, reviewers included, and persisted it whole, so a multi-megabyte name was rewritten by every `persistUsers()` and handed to every reader of `/api/users`. **Changing the account email re-verifies the current password**, like the password branch beside it: the address is how an account is recovered, so a hijacked session could otherwise walk it away. **`/api/auth/connect` and `/api/auth/update` read with `MAX_AUTH_BODY`** rather than the 10 MB default. **The two publish-bookkeeping blobs** (`guano-published-baseline`, `guano-published-info`) need a build role AND a session: they are not project blobs, so no merge covered them, and a token is judged by **how it authenticated** rather than by its owner's role — a token is minted by an admin, so `isBuildRole(user.role)` is exactly the wrong question and waved every agent through. **A private site's MEDIA is private too**: `/media/:id` was dispatched before `handleStatic`, which is where the gate lives, so the pictures answered to anyone holding a link. **A malformed percent-escape is a 400**, through `safeDecode` at all nine decode sites — `GET /%E0` reached the global catch and answered "internal error (ref …)" with a logged stack, which is a log-spam primitive. **`log.mjs` collapses control characters** in a message: a value that reaches a log line from a request (a data-URL mime off a contributor's node, an XFF under `TRUST_PROXY`) could carry newlines and write extra "lines" with a timestamp and level of its own choosing; `LOG_JSON` was never affected. **The preview mount sends `referrer-policy: no-referrer`** and its cookie carries a server-checked `<exp>.<hmac>`: the `?t=` token sat in the url every third-party image in the draft would send as a Referer, and `Max-Age` is the browser's to honour, so anyone who ever opened a preview kept draft access until `preview.secret` was hand-deleted. The preview directory is **0700** — it renders unpublished work and was made 0755 like the live site. Coverage: `e2e/store-agent-security.spec.ts`, `e2e/store-site-password.spec.ts`.

**The editor's autosave names the bytes it read.** `usePersistence.persistMerged` already reads the stored blob, three-way merges onto it and writes the result — so a save that landed BETWEEN that read and that write was erased, with every call reporting success, and what a lost update costs here is not a field but every page the other writer had. The MCP server has sent `If-Match` since it existed and gets a 412 for exactly this; the browser editor kept last-writer-wins, and that was the hole. It now sends `If-Match` too, on every project PUT. **The client never computes the hash**: `crypto.subtle` needs a secure context, and an editor reached over plain http at a LAN address is precisely the case that broke `crypto.randomUUID` (→ `src/lib/shared/ids.js`) — so the SERVER reports it, in an `x-guano-hashes` header on the store GET (a header, because the body's shape is `{key: value}` and every reader of it would otherwise have to learn a new one) and as `hash` on the PUT's own response. The PUT reports the hash of what it **wrote**, which is not always what was sent: a contributor's blob is content-merged server-side and a reviewer's is reduced to its comments, so a client hashing its own body would name a condition the server never stored and every following write would 412 against bytes nobody has. The header carries the hash of the STORED bytes even when the value is redacted for a contributor, because the condition they are naming is "the stored copy has not moved" and not "the copy I was shown". A **412 is deliberately not retryable** in `src/lib/store.ts`: replaying the same body is the clobber the header exists to prevent, and the condition never clears on its own — so the op is dropped, the blob is re-read, and `useNotice` says *"Someone saved this branch"* and names the undo history, which is the part that cannot survive (it holds whole snapshots of a document that has moved, so replaying one would put our version back over theirs). Never silently: a view refreshed with no word is a person retyping work they can no longer see. Coverage: `e2e/ui-persistence.spec.ts` forces the race — the editor's PUT is held at the route while a second builder writes the blob from outside the page — plus `e2e/store-concurrency.spec.ts` for the server half.

## Agent policy

`server/agent-policy.mjs`, `GET/PUT /api/agent-policy` — `set_target` puts the Main-vs-draft choice in front of the human via **MCP elicitation** when the client supports it (Claude Desktop) — a real dialog whose answer is the consent; only on clients without elicitation does it fall back to the agent-asserted `chosenByUser`/`acknowledgeMain` booleans. Those attestations — and `forcePurge` — are values the **agent itself** passes, so a prompt-injected agent can set them all, and even the dialog rides through the client rather than an authed channel. The real boundary is server-side and keys off how the request authenticated — `isAgentRequest` (a `guano_` bearer, no session cookie; mirrors `requestUser`'s precedence). Four switches, **all off by default**: `allowMainWrites` (write/delete `guano-project:main`), `allowPublish` (`POST /api/published`), `allowCustomCode` (any change to `settings.customCode` or a page's `customCode` — raw `<script>` on every published page), and `allowFormSubmissions` (READ form submissions — site visitors' names and messages, which an injected agent could exfiltrate through any write it can make; no switch ever allows deleting one). Changing `settings.publishing` from a token is refused outright, policy or not. The endpoint is **admin + session-cookie only**: a token able to flip these would guard nothing. With the defaults an agent works in a draft, cannot publish, and cannot ship script — so a successful injection costs a bad draft a human reviews, not the live site. **The switches are edited in Settings → MCP → Agent permissions** (an admin-only `SettingsGroup` beside the token list), and the two that every connected instance needs answered — `allowMainWrites` and `allowPublish` — are ALSO asked at the two onboarding moments, through `onboardingPolicy` (only those two keys, only booleans): the first-run **setup form** (`SetupView`'s "AI agents" section, sent as `agentPolicy` on `POST /api/auth/setup`, applied after `createFirstAdmin` succeeds — creating the first admin is already the trusted moment) and **`guano connect`** (`--main` / `--publish`, or two readline questions defaulting to No; `--yes` skips them and leaves the policy alone; sent as `policy` on the nonce-trusted, loopback-only `POST /api/auth/connect`, which answers with the resulting `agentPolicy`, or written straight through `agent-policy.mjs` when the server is down). When Main ends up allowed, `connect` writes `GUANO_MCP_TARGET=main` into the client config so the agent never asks for a target. **Both happen BEFORE the server has ever run, too**: `npm create @useguano` asks "connect Claude Desktop?" plus the two questions and runs `guano connect --offline` through the just-installed package, which mints a **pending** API token (`userId: null, pendingFirstAdmin: true` in `api-tokens.json` — `apiTokenUser` refuses it, `listApiTokens` lists it under nobody) and writes `agent-policy.json` into `<dir>/data`; `createFirstAdmin` calls `bindPendingTokens`, so the first admin owns it the moment the account exists, and `GET /api/auth/me` in the needs-setup state returns the preset `agentPolicy` (`agentPolicyPreset`, i.e. the file exists) so `SetupView` shows the answers instead of asking again (`useAuth.presetAgentPolicy`, and `setup()` then sends no `agentPolicy`). `--offline` exists because a server on the default port may be ANOTHER project's, and minting through it would connect Claude to the wrong instance. Coverage: `e2e/auth-pending-token.spec.ts`. Settings is where they change afterwards, and the reason every refusal names that exact path: they used to say "enable agent Main writes in Settings" when Settings held no such control, so the only way to allow anything was hand-editing `agent-policy.json` in the data dir — and since a fresh instance has no such file, every agent was permanently unable to touch Main with nothing in the product to change it. `GET /api/auth/me` reports the policy as `agentPolicy` **to a token only** (writing it stays admin + session), so `get_status` carries `permissions` plus a `mainWritesNote` and `set_target` marks a Main target `mainWritesDisabled` with the sentence to read out — the refusal arrives when the target is chosen instead of as a 403 on the first save after an hour of work. A Main target is still ACCEPTED when the switch is off, because refusing it would leave a client configured with `GUANO_MCP_TARGET="main"` no target at all, and so no possible write anywhere. **The editor's AI drawer surfaces the same switch where the refusal is seen**: on Main with `allowMainWrites: false` it shows *The AI can't edit Main yet* above the transcript, with an **Allow** button for admins that sends this same `PUT /api/agent-policy` — the one Settings → MCP → Agent permissions sends, not a second endpoint. The panel never asks for a target (`docs/mcp.md`, Embedded mode), so the Main decision is the only agent-permission question left in front of the person, and it belongs in the surface where the work is.

## Integrations

`server/integrations.mjs`, `src/lib/shared/integrations.js`, `GET/POST/PUT/DELETE /api/integrations` — an integration is a **named set of keys** the user creates — not one fixed group per provider — so a site can wire up anything (`SMTP {HOST PORT USER PASSWORD FROM}`, `Zapier {FORWARD_URL}`, `Stripe {PUBLISHABLE_KEY SECRET_KEY}`). A key is **secret** (write-once, masked, never returned) or **plain** (readable, and substituted into custom code). **The WHOLE integration lives server-side** in `server/data/integrations.json`, not just its secrets: while `settings.smtp.host` sat in the project blob and only the password sat server-side, anyone who could write that blob — an editor, a draft, a 3-way merge, a contributor, an agent token — could point the host at their own machine and read the password off the first `AUTH`. `ProjectSettings.smtp`/`.integrations` are deprecated optionals that `migrateIntegrations` carries across once at boot and then **deletes from every blob**. **Reads** are session OR a `guano_` token at admin/editor (an agent needs the key NAMES to write a valid `{{ENV.X}}` reference; `publicIntegration` has no branch that can include a secret value); **writes** are admin + session cookie only, like `/api/agent-policy`. A stored secret can never be flipped to plain — delete and re-add. `envName` (shared) is the one spelling of `<INTEGRATION>_<KEY>`, used by the panel, the exporter and the MCP listing; two names that normalize to the same prefix are refused at write. The exporter substitutes `{{ENV.…}}` in **custom code only** (never node content, which is user data) and **fails the export** on a reference to a secret or unknown key — a warning would ship the page.

## Capabilities

`server/capabilities.mjs` — the server does not know which integration "is SMTP". A capability declares the keys it `needs`, an admin **picks** an integration for it (Settings → Forms), and `resolveCapability` validates the pick and returns the key bag; a missing key is refused **by name** ("Postmark is missing PORT"), at pick time and at send time, with the same message. `verifyCapabilityPick` is the stricter pick-time check — for `webhook` it also resolves the URL through `net-guard.mjs`, so one aimed at the operator's LAN is refused while the admin is still in the dialog. `smtp`'s HOST allows a **single label** (`localhost`, a compose service name): requiring a dot rejected exactly the self-hosted local-relay case. `server/smtp.mjs` is a zero-dependency client (the `zip.mjs` precedent): AUTH never in plaintext (STARTTLS required off 465, torn down rather than falling back), certificate verification on and checked against the real host (omit `host` on the upgrade and node checks the cert against the literal "localhost"), every header value **throws** on CR/LF/NUL, body dot-stuffed.

## Forms

`src/lib/shared/forms.js`, `node.form`, `server/public/*` — a `form` is plain until `form.enabled`, then it posts to **`POST /_guano/forms/:id`** — the only unauthenticated write in the product. A form that is NOT enabled exports `method="dialog"` plus `data-form-inert`, because a bare `<form>` still submits natively — Enter in a text field, or any `<button>` with no `type`, GETs the current route with every named control in the query string, which on a questionnaire puts the answers in the address bar, in history and in the host's logs. The dialog method is abandoned by the browser after constraint validation, so nothing is sent and native validation survives; both Vue renderers already `preventDefault`, which is what kept this invisible until the published page. `publish` warns (`form-not-enabled-has-fields`) when such a form holds named controls. It lives **outside `/api`** (every mutating `/api` route is cookie-authed and same-origin-checked; one loosened guard must not expose both) in the namespace the site-password unlock already owns, which is also why the preview server can serve its twin. It validates against the **manifest written at publish** (`forms-manifest.json`, never inside `site/`), not the live project and never the request: the visitor submitted the page that SHIPPED. Refusal order is cheapest-first — CORS, id shape, rate limits, manifest, content type, 32 KB body, honeypot/`_t` (answered as **success**, so a bot learns nothing), `_route`/`_entry` against what was exported, then the field allowlist. `node.form` says only *whether* it notifies: recipients, the mailer and the webhook are admin-only server state (`publish.json` → `forms`), because a recipient field in the blob would let a draft, a merge or an injected agent redirect other people's leads. It is outside the contributor content allowlist. `form-success`/`form-error` are **elements** (the `list-empty` precedent) emitted hidden; `validateTree` reports a misplaced or duplicated one and a nested form. Submissions are JSONL per form, 0600, no IP and no user agent, capped (20 MB / 10 000 → `503`), pruned on `forms.retentionDays`. Reads are admin/editor; an agent token needs `allowFormSubmissions` (off by default) and gets every value **fenced**; nothing deletes with a token. CSV quotes per RFC 4180 and prefixes `= + - @ TAB CR` with `'` — visitors write those cells and a spreadsheet executes them. A site published as zip/GitHub reaches the instance through `settings.publishing.apiOrigin`, which agents and contributors already cannot write.

## Redirects

`settings.redirects`, `src/lib/shared/redirects.js` — 301s, `{id, from, to}`. **The invariant is that a redirect can never cost a PAGE**: `resolveRedirects` runs at EXPORT time against the routes that actually shipped (`written`, the authoritative list), so a rule whose source is a real route is dropped and reported instead of served — which is what lets the server answer a redirect BEFORE it looks for a file (`serveSiteDir`), i.e. a real 301 rather than the meta-refresh stub. The stubs are written anyway, because `site/` IS what the zip ships and a static host cannot answer a 301 of its own; the `server` method never reads them. A chain is collapsed to one hop and **stops at a published route** (following it past a live page was the one outcome a redirect must never produce), a source with no locale prefix gets a per-locale twin (a slug is shared across locales, so a rename would otherwise break every translated route), and `from: '/'` is refused. Served from **`data/redirects.json`** (written after a successful export, like `forms-manifest.json` — answering a redirect must not parse `published.json`), read through `manifestReader`, whose 5s cache a publish now **invalidates** (`read.invalidate`) — without it the live site kept answering the previous publish's rules for five seconds, which is exactly the moment someone is watching. The 301 carries `cache-control: no-cache` deliberately: a bare 301 is cached by browsers indefinitely, so removing a rule later would leave every visitor who followed it permanently stuck. In the editor: Settings → Site → **Redirects**, plus the two prompts that make it a feature rather than a list nobody opens — `PageSettingsEditor` offers the 301 when a slug changes (from the path the item had before the first change of this session, so /a → /b → /c offers /a) and reports when the current path is itself a redirect source. **Both alerts can be true at once** and are independent, because renaming back onto an old path asks two different questions. Their per-id marks are `reactive(Map|Set)`, not plain ones: `redirectOffer` early-returns before touching `page.path`, so a plain Map read was never a dependency and the computed stayed on the `null` it returned at mount (the `useElement` selection-marks rule again). MCP: `update_page {redirect: true}` (else `redirectSuggestion`), `update_settings {redirects|addRedirects|removeRedirects}`, `get_settings.redirects`, and the `redirect-shadowed` / `redirect-dangling` / `redirect-chained` publish warnings — computed in `collectPublishWarnings` off the route table the dead-link check already builds, NOT off the export stats, because the in-process harness stubs publish and a warning nobody can test is a warning that rots. Coverage: `e2e/store-redirects.spec.ts` (the served 301), `e2e/ui-redirects.spec.ts` (both prompts), `e2e/mcp-tool-contracts.spec.ts`.
