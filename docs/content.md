## Collections

`useCollections` — CMS content types. Field types live in `lib/collectionFields.ts` (`FIELD_TYPES`, `setFieldType`, `fieldValueError`, `isTranslatableType`) — one catalog, read by the panel AND by the MCP tools through the runtime bundle, so a value the editor accepts is one an agent can write. **Every value is a string**, `number` ("12") and `boolean` ("true"/"false") included: one storage shape, so a bound attribute, a `data-[…]:` variant and the numeric-aware sort all read the same thing. A `select` stores a VALUE and carries its `options` on the field, plus optional `optionLabels` (value → label) that `data-field="status|label"` renders — the one-`<span>`-per-option trick still works and is still how a label TRANSLATES, but it is no longer the only way to show words. Pages match on the value, which is why renaming an option never rewrites the entries holding the old one — pages match on the value, so a silent rewrite would restyle them, and the drift is reported instead. **`number`/`boolean`/`select` are non-translatable by TYPE** (`isTranslatableType`), so the worklist skips them and a locale override on one is refused. A collection owns `fields`, `entries`, and a **template page** (a real `project.pages` entry with `collectionId` + a body bound to the collection). `[field]` args bind elements to fields; a `collection-list` repeats its children per entry; a `collection-item` renders one picked entry through the template. Entry values are edited in **two** places: the **Pages drawer's item editor** (clicking an entry row opens `PageSettingsEditor`'s Content section — field values *and* name/slug/status/seo in one view, without closing the drawer) and, secondarily, on the template canvas "in entry context" (`activeEntryId` + `EntryScope`). The drawer is the primary surface because a **data-only** collection (`detailRoutes: false`, `templatePageId: ''` — creatable only via MCP) has no template page to edit through; `openEntry` bails rather than letting `setActivePage('')` fall through to `pages[0]`. **`useEntryField` is the canonical per-type read/write** (locale-aware text via `useLocale`, ids/galleries written straight to `entry.values` with "empty deletes the key"); `DataEditor.vue`'s reference/gallery writers (~:494-561) are a second, not-yet-migrated copy of the same rules — keep them in step.

## Localization

`useLocale` — base content lives on the node/entry itself (default locale); non-default locales store **overrides** in `node.locales[code]` / `entry.locales[code]`. Reads are fallback-aware and render untranslated fallbacks dimmed. Empty overrides are pruned so touch-then-clear leaves a node byte-identical (keeps merge signatures stable). `activeLocale` is runtime-only, not on the project.

## The language switcher

`@locale:<code>` as a node's `link` — THIS route in another locale, resolved by `resolveHref` in `export.mjs` and by `linkRaw` in `useRenderNode` — a plain `/…` link cannot express it, since internal links are auto-prefixed with the CURRENT locale. **The `@` is part of the sentinel**, as it is for `@item`; all three readers tested `startsWith('locale:')` and so emitted no `href` at all, on every route, which also meant `update_settings`' dead-switcher guard could never fire. Coverage: `e2e/export-locale-attributes.spec.ts`.

## A list's empty state

`list-empty` — a direct child of a `collection-list` or a bound `slider` that renders only when there is nothing to repeat, and is never repeated. The siblings are the row template and do not render when the list is empty. `useRenderNode` exposes the split as `listTemplateChildren` / `listEmptyChildren`, which both Vue renderers and `export.mjs` use; `validateTree` refuses it anywhere else, since it would never render. On the Build canvas, a list with no entries shows the row template with placeholders AND the empty block — the canvas is an editing surface, and otherwise a list for an empty collection could never be styled; with entries the empty block is not drawn and is selected from the Layers tree, like a hidden part. Coverage: `e2e/export-list-empty.spec.ts`.

## Attribute layers

`shared/attributes.resolveNodeAttributes` — what an element renders is the component master's `attributes` (shared, like classes), then each host **mirror**'s `instanceAttributes` (least specific first — a host IS a placement), then `node.instanceAttributes` for THIS placement, then `node.locales[code].attributes` for the route's locale. The mirror layer is the one every reader used to miss: a write to it was stored, read back and rendered NOWHERE, so four radios inside one component host each given their own `name` exported with the inner component's default and became ONE radio group. `mergeAttributeLayers` is the two-layer form, for a node with no mapping. Only `placeholder`, `aria-label`, `alt` and `title` are localizable (`isLocalizableAttribute`); the rest are structural and read the same in every language. The per-placement layer is what lets one component serve "Search contacts" and "Your email" instead of copying its classes onto a plain element. `edit_elements` writes the shared set with `attributes`, this placement's with `instanceAttributes`, and a translation with `attributes` + `locale`; `get_translation_worklist` emits `kind: "attribute"` items and `set_translations` writes them, so `missingTranslatable` counts them. Coverage: `e2e/export-locale-attributes.spec.ts`.

## Data-driven presentation

`node.fieldAttrs`, `shared/fields.resolveFieldAttrs` — attribute name → collection field name, resolved against the surrounding `EntryScope` by both Vue renderers and `export.mjs`. In the exporter it is resolved **before** `alt`/`href`/`src` are emitted, because those names are in the `managed` set the pass-through loop skips — bound last, a `data-bind-alt` rendered on the canvas and in Play and was empty on every published page. This is the only way presentation follows DATA: `data-status` bound to a status field lets `data-[status=waiting]:` classes render one pill in several colours, and `value`/`placeholder` bound to a field pre-fills an edit form. The static `attributes` value is the fallback when there is no entry or the field is empty, so a bound attribute stays authorable out of scope. Per-instance with a component default (`resolveInstanceValue`, like `listQuery`), carried by `cloneSubtree` on copy/paste and baked by `detach`, and refused on an instance wrapper — which renders no element, so the attribute would land nowhere. A key of `style:--x` binds a CSS custom property instead of an attribute (see below). Edited in the Data panel's Attributes rows (a field select per row) and through `edit_elements {fieldAttrs}`. Coverage: `e2e/export-field-attrs.spec.ts`, `e2e/data-bindings.spec.ts`.

## Reserved `data-*` attributes

`shared/attributes.isReservedAttribute` — `data-` is an open prefix for authors, EXCEPT the names a renderer owns — `data-form*`, **`data-fx`**, `data-slider`, `data-sl-*`, `data-channel`, `data-node-id`, `data-id`, `data-ref`, `data-type`, `data-source` (the retired `data-int`/`data-anim`/`data-tgt`/`data-atgt` stay reserved, so a blob carrying one can never shadow a future reader). `isAllowedAttribute` refuses them, so the Data panel, the HTML writer and the exporter all do. **A duplicate attribute in HTML resolves to the FIRST occurrence**, so without this an authored name shadows the renderer's own value: `data-form-redirect` is validated as an internal route at write AND at export, and the published runtime calls `location.assign` on it — set as a custom attribute it bypassed both, which bought an open redirect and (since `location.assign` honours a `javascript:` URL) script on the published origin, which under the `server` method is the origin serving `/admin` and `/api`. Setting an attribute is not gated by `allowCustomCode`, so a prompt-injected agent with publish rights could ship it. Defended three times over: the name is refused, the exporter emits its own attributes FIRST so a future gap cannot shadow them, and the runtime navigates only to a root-relative path because it is served from static hosts we do not control. Coverage: `e2e/export-forms.spec.ts`.

## Sliders

`src/lib/shared/slider.js`, `node.slider` — `slider` is a container that lays its children out as a horizontal scroll-snap track with built-in arrow/dot chrome. Two modes decided by the arg: `<slider data-source="post">` repeats its child template per entry exactly like a `collection-list` (same sources, same `listQuery` — `useRenderNode`'s `listScope` gate covers both types), while a bare `<slider>` makes each direct child one slide. Config is node-owned `node.slider` (`SliderConfig`: arrows, dots, `perView`, gap, autoplay, delay, loop, drag), edited **in the Data panel** and following the `listQuery` precedent everywhere (`cloneSubtree` on copy/paste, baked by `detach`, per-instance inside components). `perView` is keyed `'base'` + breakpoint ids, desktop-first like the class cascade; it drives a `--sl-pv` custom property that one `basis:calc()` on every slide reads, with `max-[Npx]:` variants for the overrides — so the canvas resolves it per frame (`perViewForWidth`, since media queries can't fire in a fixed-width frame) while Preview and the export use the real variants. **All the math, the class strings and `initSlider` live in `shared/slider.js`**, imported verbatim by both Vue renderers, the exporter, the MCP validators and the published runtime; Preview runs the same `initSlider` the live site does. The browser driver is `src/slider/runtime.ts` → committed `server/slider-runtime.js`, emitted as `/assets/slider.js` **only for routes carrying a slider** (its own gate — the interaction runtime's `hasInteractions` would miss a slider-only page). The track is a real scroller and never writes `transform`, so it can't collide with animations' inline styles or break `position: fixed`. Autoplay yields to `prefers-reduced-motion` / `?noanim` and never runs on the Build canvas. **The chrome's Tailwind classes are renderer-invented, so `collectCandidates` must register them** (`sliderCandidateClasses`) or they never reach the published stylesheet. **So are its WORDS**, which had the same problem one layer over: "Previous slide" / "Next slide" / "Slides" / "Go to slide N" were English literals in all three renderers and in the runtime's dot builder, so they lived in no tree, nothing translated them, every `/fr/` route shipped English and `get_translation_worklist` reached `missingTranslatable: 0` with them sitting there. They now resolve off the node's ordinary localizable attributes (`SLIDER_LABEL_ATTRS` → `data-prev-label`/`data-next-label`/`data-dots-label`/`data-dot-label`, added to `LOCALIZABLE_ATTRS`), so `node.locales[code].attributes` — already read by all three renderers, already enumerated by the worklist and the `untranslated-attributes` warning, already written by `set_translations` — carries them with no schema change. Deliberately NOT under the reserved `data-sl-` prefix: that prefix exists to stop an authored name shadowing a value the renderer owns, and here the renderer WANTS the authored value. They are **consumed, never emitted** (the exporter's `managed` set and `customAttrs` both strip them), and the **dot pattern travels on the wire** (`data.dl`, omitted when it is the default) because only the runtime knows the reachable count. `withSliderLabels` in `tools.mjs` synthesizes the four with their effective values so an unauthored slider still offers them to translate.

## Icons

`src/lib/shared/svg.js`, `node.svg` — `icon` renders an inline `<svg>` — the `<svg>` IS the element, so classes land on it and it follows `currentColor`, which an `image` of an SVG never can. `node.svg` is always the output of `sanitizeInlineSvg`, a **strict allowlist** that rebuilds the markup from known elements, known attributes and a known value charset, and recolours every paint to `currentColor`. It is sanitized where it is written **and** where it is rendered — a project blob can arrive by import, merge or agent without passing any writer, and the exporter is the line where markup becomes a page. This is NOT `server/media.mjs`'s `sanitizeSvg`, which guards uploaded files that are only ever an `<img>`. **That one used to be four regexes matching LITERAL names, and the two things they could not see are the two that matter.** XML lets a document bind any prefix to a namespace, and a browser honours the element when the file is navigated to directly, so `<svg xmlns:s="http://www.w3.org/2000/svg"><s:script>` passed untouched; and an attribute value is entity-decoded by the parser AFTER a regex looks at it, so `href="&#106;avascript:…"` and `href="java&#9;script:…"` passed too. It is a small tokenizer now: it matches an element's LOCAL name whatever prefix carries it, decodes entities and strips whitespace and control characters before judging any URL, refuses an animation that writes `href`, and re-emits any tag it dropped nothing from as the ORIGINAL BYTES — which is what keeps a real icon (`<use href="#id">`, `fill="url(#g)"`, Inkscape's namespaces) exporting identically and `check:corpus` honest. The served `default-src 'none'` CSP + nosniff is still the second layer, and it is the layer that covers the `server` publish method; **a site published as a zip or to GitHub is served by a host that sends whatever it sends, and there this pass is the only layer there is.** Coverage: the bypass fixtures in `e2e/store-agent-security.spec.ts`. A bundled (Lucide) pick and a custom SVG are the same thing downstream; the root's `data-icon` records which bundled icon it is. The full table is loaded on demand by the picker and imported lazily by the MCP tools — never statically, and never into the MCP runtime bundle.

## Custom code

`custom-code`, a leaf whose `content` is raw HTML — emitted VERBATIM by the exporter inside a `<div>` wearing the element's classes — the one leaf no sanitizer touches — and drawn as a placeholder box (icon + first line) on the canvas and in Play, never rendered live in the editor. `editableText` excludes it (a contenteditable would hand it to the rich-text path); it is edited in the Data panel's **Code** textarea, build roles only. Because it ships script it is gated exactly like page custom code: `codeSurface` in `server/agent-policy.mjs` walks every page tree and every component master for `custom-code` nodes (content + locale overrides), so `protectedWriteDenial` refuses a contributor's change by name and an agent's unless `allowCustomCode`; `overlayNode` in the contributor merge skips its content as well. In the HTML layer it is `<custom-code>`: the serializer ALWAYS escapes its content, `apply.ts` takes a write with real tags inside verbatim and decodes an escaped echo (a leaf's interior is never tokenized, so a `<script>` inside never meets the parser's refusal), and `edit_elements {content}` skips `sanitizeRich` for it. `{{ENV.…}}` is NOT substituted in it (that pass covers `settings.customCode` and page `customCode` only). Coverage: `scripts/check-html.ts`, `e2e/store-reviewer-code-zip.spec.ts`.

## Value formatting: `|format` on the binding path

`splitFieldFormat` / `formatFieldValue` in `shared/fields.js`, stripped and returned by `resolveBinding` so all three renderers resolve the format where they resolve the field.

`data-field="due|date:long"` and `data-field="status|label"`. Dates go through `Intl.DateTimeFormat` with a named preset (`numeric`, `short`, `medium`, `long`, `month-day`, `month-year`, `time`, `datetime`), so a `/fr/` route localizes for free; a date-only value is pinned to UTC, because parsing `2026-03-12` as UTC midnight and formatting it in a western timezone renders the day BEFORE. A choice's words come from `field.optionLabels` (value → label), which pages never match on — the VALUE is what a `data-[…]:` variant tests, so renaming a label can never restyle an entry.

The format travels on the `arg` rather than in a node key of its own because it is part of the ADDRESS — "this field, rendered this way" — and `arg` already has three readers. A second key would need carrying by `cloneSubtree`, baking by `detach` and resolving along the instance chain, for a string that means nothing without the path beside it.

A format that does not suit its field is refused at write (`fieldFormatError`) and reported by `validateTree`. Before this, two collections grew a `due-label` text field apiece to hold words a date already contained, and every status pill was five spans with four of them hidden. Coverage: `e2e/data-bindings.spec.ts`.

## A number reaching a style: `style:--x` in `fieldAttrs`

`cssVarsFromFields` in `shared/fields.js`. A `fieldAttrs` key of `style:--p` binds a CSS CUSTOM PROPERTY instead of an attribute; `resolveFieldAttrs` skips those keys so one never becomes an attribute literally named `style:--p`.

This is the ONLY way a measurement reaches CSS. A `data-[…]:` variant matches a value it has to know in advance, and a progress bar is a continuum — so `{"style:--p": "progress"}` plus `w-[calc(var(--p)*1%)]` is the whole recipe. A custom property deliberately, not a direct `width`: the style attribute is already owned by the background layer and by an animation's primed first frame, so a bound declaration would fight them, while a variable is read by a class and the cascade resolves it as usual. Values are stripped of `;{}<>"'` — a custom property's value lands in a style attribute, so it must not be able to close the declaration and open another.

Merged into `motionStyle` in `useRenderNode`, which both Vue renderers already bind at every call site, so one merge reaches all of them; the exporter joins it onto the same `style` attribute. Coverage: `e2e/data-bindings.spec.ts`.

## A list takes SEVERAL conditions

`applyListQuery` applies `query.filter` and then every entry of `query.filters`, ANDed. One condition could not express "this project AND still to do", so a per-project kanban had to be a global board — the filter was the whole gap, not the board. Each condition takes the same shape, plus `not` to invert that one. `edit_elements` validates every condition, not just `filter`: written for `filter` alone, a second condition went unvalidated and the slug-that-matches-nothing and the `equalsCurrent`-that-can-never-match were both back.

## Aggregates: a number over a list

`parseAggregate` / `aggregateValue` in `shared/fields.js`. `data-field="@count:task"`, `@sum:task.points`, and `avg`/`min`/`max`. The `@` prefix is already reserved by the lexer (`@pages`, `@item`), so this can never collide with a field named "count".

**It reuses the element's own `listQuery`**, which is the point: a column header saying "3" and the column it labels run the same `resolveListScope` + `applyListQuery` pair, so they cannot disagree. An aggregate also makes a route stateful on its own (`routeUsesState`), because a count that never moved when a card changed column is the bug it exists for — the state runtime recomputes every `data-ds-agg` whenever any entry changes, rather than tracking one per entry. Numeric ops ignore values that are not numbers, so a half-filled field sums the rest instead of rendering NaN. Coverage: `e2e/data-aggregates.spec.ts`.
