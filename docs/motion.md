## Motion — two systems, one panel

`src/components/editor/interactions/` — **interactions** (`useInteraction`) toggle Tailwind classes on hover/click/appear/scrolled/change/load (the `change` trigger listens to both `change` and `input`, forces state from checked/non-empty rather than toggling, and fires in all three renderers — both editor surfaces wire `fireChangeInteractions` from `useRenderNode`) and are still the right tool for discrete state (a `hidden`→`flex` menu; `lib/shared/interactionClasses.js` removes conflicting base classes while fired — its `splitVariant` splits on the last colon at bracket DEPTH 0, because `lastIndexOf(':')` cut `[color-scheme:light]` into the variant `[color-scheme:` and the base `light]`, so two arbitrary properties with one name were never one conflict group: a toggle's `[color-scheme:dark]` landed BESIDE the base, source order decided, and the published toggle did nothing while every tool reported success. An arbitrary property's group is its property name — `arbitrary:<prop>`, matching `propKey` in `styles.ts` — which covers custom properties (`[--bg:…]`) too; `scheme-*` is one group and so is `dark`/`light`). **Animations** (`useAnimation` + `useMotion`) are real tween timelines: `project.animations` holds named `Animation`s (ordered `steps`, each tweening property `tracks` with duration/easing/offset/stagger/repeat/yoyo), `node.animations` holds `AnimationBinding`s (trigger `load|appear|scrub|hover|click|scrolled|change`, target, `action`, appearMode, `scrollAt`, scrub range, breakpoints). **The two engines take the same triggers**, with TWO exceptions: only a timeline can `scrub` or follow the `mouse`, because both are continuous progress and a class is on or off. So `load` works on a class change (a state the page simply starts in) and `scrolled`/`change` work on a timeline (a header that shrinks by tweening), each symmetric in both engines and each refusing an `action`. `effectTriggers.ts`'s `kinds` is therefore `BOTH` everywhere but `scrub` and `mouse`. **A `click` play is keyed per (animation, target)** — `animationStateKey`, the tween counterpart of `interactionStateKey` — so an open button, a close button and an overlay drive ONE timeline and `action: on|off` aims it, exactly as it does for a class change; `off` rewinds, so the exit is the entrance played backwards and no second timeline is needed. Every other trigger stays keyed per binding (`animationBindingKey`): `load`/`appear`/`scrub` have no state to share, and `hover` is symmetric, so sharing one play would make a second hover trigger restart the timeline under the first one's pointer. `animationPlayKey` is the one place that choice is made, shared by `useMotion`, the exporter and the published runtime. On the wire the click binding carries `s` (the play key) beside `k` (still the per-binding key the tween listener list and the breakpoint gate read) and `ac` for a non-default action. **All the math lives in `src/lib/shared/motion.js`** — property catalog, easings, `compileAnimation`, `sampleAnimation`, validators — and is imported VERBATIM by the editor (`useMotion`), the exporter, the MCP validators, and the published runtime, so the canvas preview and the live site cannot drift. The browser driver is `src/motion/runtime.ts`, built by `vite.motion.config.ts` into the committed `server/motion-runtime.js` (rebuild with `npm run build:motion`; `export.mjs` throws a clear error if it's missing). **`?resetstate` forgets every remembered `once` state** (`site-runtime.js`), for the author rather than the visitor: a persisted toggle is restored on load, so the next session's first click turns it OFF and reads as a broken toggle — and the storage keys are route-local ordinals (`guano-int:<interned key>`), so there is no key worth clearing by hand. **`Interaction.modal`** makes the effect's target a real dialog while it is on: page scroll locked, focus moved in and trapped, `role="dialog"` + `aria-modal="true"` set, and every bit of it given back on off, including focus to whatever opened it. Not a native `<dialog>` — that renders nothing until opened, its user-agent centring fights the `fixed inset-0 flex items-center` classes every existing overlay is built from, the Build canvas would have to force it open, and the exclusive-group / `closeOn` model would exist twice; the flag adds the missing behaviours to the model every project already has. It is a property of the EFFECT, like `closeOn` and `group`, so the exporter records it per state key (the manifest's `modal` list) whichever binding declares it, and `server/site-runtime.js` hooks `set(key, on)` — after `apply()`, so the panel already wears its open classes when focus moves into it. **The scroll lock needs a handshake**: `src/motion/runtime.ts`'s inertia scroller hijacks the wheel and writes `window.scrollTo`, so `overflow: hidden` alone left the page moving under the panel; the wheel handler now stands down while `document.documentElement` carries **`data-guano-modal`** (which is also the CSS hook authors get). The group-eviction and dismissal paths close the modal too — they bypass `set`. On the **Play** surface `useRenderNode` mirrors the aria attributes and the focus move but NOT the scroll lock, deliberately: the preview pane is not `window`, and locking the admin shell's scroll would be wrong; the Build canvas gets neither, since stealing focus from whatever the author is typing in would be worse than the missing ring. Edited as a **Modal** toggle on the effect's class row (`StyleEffectEditor`), and as `modal` on `create_interactions` / `update_interaction`. Coverage: `e2e/interactions.spec.ts`.

## The `count` track writes text, not style

**`count` is the one track that writes TEXT**, not style (`kind: 'text'` in `MOTION_PROPS`): a number tweening up to the value the element already says. `sampleText` formats it (`Intl.NumberFormat` in the route's locale, plus `decimals`/`group`/`prefix`/`suffix` from `track.format`), and `composeMotionStyle` skips it. **The rule: a count's `from` is NEVER baked into the exported HTML** — `initialStyle` and `endStyle` ignore `kind: 'text'`. The exporter bakes `initialStyle` so an entrance never flashes its final state; for a number that would ship `0` as the text a visitor without JavaScript, and every visitor with reduced motion, reads forever. **The authored text IS the destination, and that is now a mechanism rather than a convention**: `parseCountText` reads the number an element's own text says (the exact inverse of `sampleText`, so `format` drives the read) and `countToFor` hands it to `sampleValues` as `opts.to`, a per-ELEMENT override of the shared track — the counterpart of `opts.current` at the other end of the tween. It has to be per element because `to` lives on the shared `Animation` in `project.animations`: one compiled track serves every binding and every instance, so a count bound on a component MASTER ended all four stat cards on the master's number while the HTML held the right ones (12/99/11/140 all read 12 — the markup was correct and the first frame overwrote it). That makes binding ONCE on a master with a different figure per instance the normal way to build a stat row. `track.to` is only the fallback for text holding no number, and `parseCountText` is deliberately strict — a text it cannot read (words, a `format` that does not round-trip) returns null rather than guessing. Three readers: the published runtime caches each element's authored text in a `WeakMap` read BEFORE the first write (`write()` replaces `textContent` every frame, and the scrub path rebuilds its `Play` per scroll frame, so re-reading would take a mid-tween number as the destination); the canvas and Play pass `contentInfo`'s resolved per-instance, per-locale content, which is data and never moves. The runtime writes the first frame, and `still` mode (`?noanim` / reduced motion) never touches `textContent` at all. It lands only on a **leaf that carries text and is not field-bound** (`countTargetError`, shared by the MCP bind path and the editor's), is refused in a **staggered** step (the children have no number to count), beside **`yoyo`** (it would end on the starting number), and on an element whose own text the track's `to`/`format` cannot read back (compared with separators normalized — `Intl` groups with U+202F/U+00A0 and nobody types those). The INSTANCE half of that last check is `publish`'s `count-text-unreadable` warning, since only a whole-project pass knows what every instance says. "Count" appears in `TimelineEditor`'s property list on its own (the list is derived from `MOTION_PROPS`), with prefix / decimals / suffix / grouping on a second row shown only for a count track; `track.format` is in the `create_animations` schema. Coverage: `e2e/site-motion.spec.ts`, `e2e/mcp-tool-contracts.spec.ts`.

## A track's `from` is the resting value

**A track's `from` is the element's RESTING value, on every trigger** (`primeFirstFrame` / `primeFirstFrameValues` in `shared/motion.js`): per property, the explicit `from` of the timeline that starts earliest (binding `delay` + track offset) is what the element wears until something plays. It used to be primed for `load`/`appear` only — "hover/click/scrub start from the natural state" — so a hover tweening opacity 0 → 1 shipped VISIBLE and then snapped to 0 on the first hover frame before fading back in, which reads as a flash and makes the authored `from` look ignored. All four readers now prime the same way: the exporter bakes it into the inline `style` (still never for a breakpoint-SCOPED binding — an inline style has no media query), the published runtime primes what the export could not and, critically, **`clear()` puts the primed frame BACK** rather than emptying the inline styles (a hover rewinding to t=0 deletes them, which restored the natural value and lost the resting state), and Play merges it UNDER the playing values in `useRenderNode.motionStyle` — on VALUES, not styles, or a composed `transform` would replace another timeline's wholesale. A track that omits `from` primes nothing, which is what keeps the ordinary "tween from wherever it is" hover untouched; a `count` is never primed; and **a `from` equal to the property's own default** (`rotate: 0`, `scale: 1`, `opacity: 1`) primes nothing on a trigger that fires LATER — it states nothing the element is not already rendering, and an inline value beats a class, so a baked `transform:rotate(0deg)` would silently drop the `active:scale-95` beside it; it still DECIDES the property, or a 0 → -10 → 8 → 0 wiggle would rest at the next track's -10. An **entrance** keeps baking its `from` whatever it is (`entrance` on the entry, set for `load`/`appear` and for a page transition's `initialStyle`): that frame exists to defeat the stylesheet before the runtime boots, which is what makes the GUIDE's "put the pre-play state in `from`, not in a class" true — and it is why the corpus stays byte-identical. **Play only** (`useRenderNode`'s `restingMotion` option, passed by `PreviewRenderer` alone): no trigger fires on the Build canvas or the components board, so priming there would leave an element whose timeline starts at opacity 0 permanently invisible on the two surfaces it is edited from.

## A staggered step primes the children

**A STAGGERED step primes the target's CHILDREN**, and that is where its `from` has to land: the cascade moves them, so the target itself holds nothing and a staggered entrance used to ship every child at its FINAL value — the page painted the finished section, the deferred runtime booted, wrote the `from` on its first frame and played forward, which reads as a flash before the animation on every load. The exporter bakes the staggered half onto each direct child (`staggerPrimeEntries` + `buildParentIndex` in `export.mjs` — a child has to ask what its parent primes, because a parent's attributes are emitted AFTER its subtree renders) and Play asks the same question through `restValuesFor`'s `part: 'staggered'` entries. Both halves go in ONE `primeFirstFrame` call, since an element wears one resting frame whichever timeline decides each property — an element that is both a stagger child and its own target composes the two into one `transform` rather than one replacing the other. Every trigger, by the same rules as the element half: a breakpoint-SCOPED binding is still never baked, and a **`staggerSelector`** is matched in the DOM, which the exporter cannot evaluate, so those stay primed by the runtime. This is the one deliberate corpus re-baseline in the priming work — the diff is a `style` attribute added to staggered children and nothing else. Coverage: `e2e/site-motion.spec.ts`.

## The `mouse` trigger

**`mouse` is the second continuous trigger** (`AnimationBinding.mouse`, `mouseProgressRaw` in `shared/motion.js`): the pointer's position along ONE axis, 0..1 across a box, driving the timeline's progress — Webflow's "Mouse move". Three things make it a feature rather than a trigger name. (1) **The box is the BINDING's element, and the target is what moves** (`area: 'element'`, the default; `area: 'page'` measures the viewport instead), so a follow is bound on the stage and aimed at the card, and one pointer drives every child off one trigger. (2) **One binding is one axis**, because a timeline carries one progress — a 2D follow is TWO bindings on the same trigger, which `mergeForElement` (runtime) and `motionStyle` (Play) already compose per PROPERTY into one `transform`. That is also why the "one action per trigger view" change above had to land first: before it, the two were an unaddressable stack. (3) **A follow REST at the MIDDLE of its timeline, not at its track's `from`** — the one trigger whose resting frame is not `from`. `MOUSE_REST` is the shared number and `primeFirstFrameValues` takes a `mid` entry that samples `duration * MOUSE_REST` instead of reading the tracks; for the symmetric `-n → n` case that sample IS the property's default, so nothing is baked and no class is shadowed, while an asymmetric one bakes its true middle. Priming `from` instead shipped the element shoved hard to one end of its travel — to every visitor before the deferred runtime boots, and permanently to one on `?noanim` or reduced motion. All four readers prime through the same helper (`export.mjs`, `src/motion/runtime.ts`, `useMotion.restValuesFor`), and all three drivers hold a fresh binding at `MOUSE_REST` and ease away from it (`approach`, shared with the scrub loop, default `smooth: 0.12`s — a follow with no catch-up reads as a jump). The driver stands down on a **coarse pointer** (a touch drag fires `pointermove`), under reduced motion and on `?noanim`. On the wire it is `o.mo`, carrying only what differs from `MOUSE_DEFAULTS`. `delay` and `action` are refused by `validateBinding` — nothing fires a follow and it has no second direction. In Play the `page` area is the preview PANE, not the window, for the same reason the modal scroll lock is not applied there. Coverage: `e2e/export-mouse-follow.spec.ts`, `e2e/mcp-tool-contracts.spec.ts`, `e2e/ui-interactions-panel.spec.ts`.

Animations write **inline styles**; interactions write classes — never animate the same property with both. The runtime honours `prefers-reduced-motion` and `?noanim` by jumping to each timeline's end state. Both systems share the `pickingFor` target picker, and the `bindingId@instanceId` key convention that keeps component instances independent. **`useMotion` carries a play's scope on the `PlayState`, never parsed back out of its key**: a channel target puts an `@` inside the key itself (`animId:@start`), so neither the first nor the last one is reliably the scope separator, and `inScope` compares the stored value instead. **The UI never names either engine** — see the panel below.
## The panel's shape: trigger-first, and everything else one surface down

`src/components/editor/interactions/` + `src/components/editor/effects/` — The panel asks **when**, then **what**, and never names an engine: `src/lib/effectTriggers.ts` is the one trigger table, and its `kinds` is what silently filters the action picker (`load`/`scrub` offer tweens only, `scrolled`/`change` class changes only, `hover`/`click`/`appear` both). **The popover is only an index**: the element's triggers as rows plus "+ Trigger", and picking either opens the effects drawer's **trigger view** (`TriggerEditor`, `useEffectsDrawer.openTrigger`) — nothing is edited in the popover, because it is a floating column that closes under a target pick, while the drawer has the canvas's width and stays put. **One action per trigger VIEW, and the index is per ACTION rather than per trigger**: a click runs one effect, so the trigger view has no list and nothing to open — it edits the ONE action `useEffectsDrawer.action` pins (the binding id, falling back to the trigger's first row), and Remove takes off that row alone. An author who wants a second motion on hover **adds hover again**: `+ Trigger` offers every `UI_TRIGGERS` entry, used or not, and the two rows sit side by side in both indexes, each with its own effect (the drawer's sidebar shows the effect name only when a trigger is repeated, so the rows are tellable apart). It used to be the other way round — one row per trigger, the view stacking every action under it, `+ Trigger` filtering out the ones already used — which made a trigger holding several (an agent's write, a component master: this project's own FeatureCard carried a `Lift` and an `Icon pop` under one hover) uneditable, since the Type pick and Remove both drove the whole stack. The drawer's left column is its index (the selected element's actions above the effect library). `useElementEffects` derives the element's states and `actions` once for both surfaces, one `ActionRow` per `EffectPair`. The trigger view is **WHERE | WHAT**: the header names the trigger and the effect (`EffectNameField`) and holds Remove / Cancel / Apply; the left column is the action's **options** (`ActionOptions`: target, direction, replay or scrub range, screens); the right is the **effect itself** (`EffectBody` → `EffectEditor`: a CLASSES band — one line, classes + duration + easing — and a MOTION band with Play and the timeline). Nothing to pick: **adding a trigger creates its action** (`useElementEffects.createActionFor` — a new effect with both halves, bound under the trigger for every half it can run), flagged `fresh` (`useEffectsDrawer.effectCreated`) so Cancel is the cascading discard of effect and binding until Apply; both close the drawer, and on a kept effect Cancel only closes, since every edit is live. There is no action picker and no State card any more: states, presets and saved effects are not offered at bind time, and `closeOn`/`group`/`once` are agent-only — both runtimes still fold them per `(interaction, target)` whichever binding declares them.

An `Interaction` (`name`/`toClasses`/`duration`/`easing`) and an `Animation` (`name`/`steps`) are shared by every element using them, so they are edited in the **effects drawer** under the canvas (`EffectsDrawer`, ⌘⇧E — `{key:'e', mod:true, shift:true}`, and the existing ⌘E palette binding carries `shift:false` or it would answer both). It is a sibling of the canvas in a flex column, not an overlay: it pushes the canvas up and leaves both bottom corners alone (Insert owns bottom-left, `ModeToggle` bottom-right). `EffectLibrary` is one merged list sorted by name — every named effect, plus every half no effect has claimed, so nothing is hidden by not being wrapped; **a new effect is born with BOTH halves** (the picker's one `New effect` — the library has no create button; an effect is made from the trigger it is for), and `EffectEditor` draws them as one flow — the class row, then the timeline — with no section naming an engine; a single-engine effect — one made before the pairing existed, by a motion preset, or by an agent — gains the missing half from one `Classes`/`Motion` button, never by merely being opened; `StyleEffectEditor` is classes + duration + easing (an easing the preset list has no name for is offered as "Custom" rather than shown as unset, so the next pick can't silently replace it); `TimelineEditor` draws `compileAnimation`'s tracks against a ruler — the same compiler the canvas, the exporter and the runtime use, so the drawing cannot drift from the play — and a drag writes back to the step's `offset`/`duration`, with the scale **frozen during the drag** or the bar would chase the pointer. `useEffectsDrawer` holds `{kind, id, created}` as **ids, never objects**, because undo/branch-switch/merge replace the whole `project` ref and a held object would silently detach; unlike the old detail view it deliberately SURVIVES a selection or panel change, which is the point of it. Creating from the picker auto-applies to the element; **Cancel discards via the cascading `deleteInteraction`/`deleteAnimation`** (never a hand-rolled removeBinding, so it works after the element was deselected or deleted), while **Escape only closes the drawer** — one layer per press, capture-phase + `stopPropagation` so it doesn't let `SettingsEditor` close the whole panel, and it stands down for a pending target pick, an open modal and a focused field. The panel works with **no single selection** (it offers the drawer instead), and `useComponents.editTarget` is still the one instance→master redirect that Style, Interactions and Animations all write through. Coverage: `e2e/ui-interactions-panel.spec.ts`.
