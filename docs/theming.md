## Design tokens

`useThemeTokens`, `settings.tokens` — the project's `DesignToken[]` are compiled into a single `<style type="text/tailwindcss">` `@theme` block in the head (debounced 200ms because each change triggers a full `@tailwindcss/browser` recompile). Distinct from `useTheme`, which only toggles the editor's own light/dark chrome via a `.light` class (a per-browser localStorage preference, not project data).

**A token carries an optional `dark` value, and that is the whole of light/dark theming** (`modeTokensCss` + `DARK_VARIANT`, both shared by the exporter and `useThemeTokens`). The light value goes in `@theme`; every token that has a dark one is emitted AGAIN under the `dark` marker class, **unlayered** so it beats `@theme`'s own `:root` block (Tailwind puts that in `@layer theme`, and an unlayered rule wins whatever its specificity) — so `bg-background text-foreground` is already right in both modes and a retheme stays one token edit. Custom properties inherit, so the marker only has to land on an ancestor. `light` is the symmetric escape (a light island inside a dark section, and the toggle for a site whose default IS dark): it re-asserts the light values and is excluded from the variant's selector.

**The switcher is a `link` sentinel** (`@theme`, `@theme:dark|light|system` — `src/lib/shared/colorMode.js`), the same shape as the language switcher's `@locale:<code>`: one existing field, no new schema, usable on any element, emitting the reserved `data-guano-theme` instead of an `href` because a theme switch is not a navigation (**both writers of `link` have to know the sentinel**: `href="@theme"` in markup is stored verbatim by `html/apply.ts`, while `edit_elements {link}` validates against an allowlist — which refused the switcher as "not a usable destination" while naming every form except the one asked for, so one field answered two ways and the feature read as nonexistent. A bad action is now refused by name there, listing the four modes) (an `<a>` still gets `href="#"` so it stays keyboard-operable, and nothing is wrapped in a `contents` anchor). **The mode is applied by a blocking inline script in `<head>`** (`colorModeScript`, ~940 B, emitted only when the project switches modes at all — `usesColorMode`, cached per project since `renderShell` runs per route). That script is the feature: a class interaction with `once: "local"` restores the choice from the DEFERRED `/assets/script.js`, so a dark-mode visitor got a full paint of the light site and a flash on every navigation, and nothing an author can write in the editor runs early enough. It also carries the third state an interaction cannot express — **nothing stored** — which is what makes `settings.theme.colorMode: 'system'` (follow the visitor's OS until they choose) possible; `resolveColorMode` is the one precedence rule, shared with the editor. The script owns `<html>`, which is also what fixes a white overscroll band on a dark site. `?resetstate` does not touch it (that is the interaction runtime's `once`); the key is `localStorage['guano-theme']` — the VISITOR's, which is why the editor chrome's own preference is `guano-editor-theme` and not that: under the `server` publish method the admin and the site are one origin, so while they shared a key, setting the chrome to light re-themed your own published site and a visitor's toggle flipped the chrome on next open. The editor mirrors it through **`useColorMode`** (runtime-only state, like the active locale): both canvas surfaces and Play wear the resolved mode on their `data-site-scope` element, Play's click applies a switcher through the same helper, and the sun/moon is `ColorModeToggle`, one pill bottom-right of the canvas on a page, in Play, and on the components BOARD (it used to be the third segment of the Edit / Play toggle, which moved to the launcher's header). A dark palette you cannot see on the canvas is one you can only check by publishing. **What the surface paints under the project is `sitePaperStyle`** (`lib/settings.ts`): the `background`/`foreground` tokens resolved for the mode being shown, on the page frames AND the board cards, which both wore a literal `bg-white text-black` before — so a dark palette flipped its tokens and kept its white paper. Resolved in JS on purpose, because `useThemeTokens` reasserts the CHROME's colours as `--color-*` on `:root` and custom properties inherit, so a `var(--color-background, #fff)` fallback could never fire: a project naming no `background` token would have painted its canvas in the editor chrome's own colour. `publish` warns for a switcher with nothing to switch (`theme-switch-no-dark`) and for dark values no visitor can reach (`dark-palette-unreachable`); `validateTree` refuses a misspelled action and a switcher on a component wrapper (it emits no element, so there is nothing to click).

**`dark:` is CLASS-based here, not `prefers-color-scheme`** — the one deliberate departure from Tailwind's default, worth understanding before "fixing" it. An interaction can only ADD classes (and evict the base classes they conflict with), which is exactly two states; following the OS needs three, so with the OS in dark a visitor's click to go light would fall back to dark and the toggle would read as broken. The toggle is therefore an ordinary class interaction (`toClasses: "dark"`, `once: "local"`), and `dark`/`light` share ONE conflict group (`color-mode` in `shared/interactionClasses.js`) so the fired class takes the base one off. Nothing in the corpus or the live store used `dark:` when this changed. The markers remain the way to build a FIXED island — a permanently dark footer on a light site — while the site-wide mode is the switcher's job. Coverage: `e2e/export-theme.spec.ts`, `e2e/mcp-publish-warnings.spec.ts`.
